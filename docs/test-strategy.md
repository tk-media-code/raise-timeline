# テスト方針

- 日付: 2026-10-06

## 1. 考え方

テストは「この入力・この状態なら、プログラムはこう動くはず」という期待をコードとして書き、自動で実行するもの。
機能が増えるほど人が手で全部を確かめるのは無理になるので、機械に確かめさせる。push のたびに品質チェック（`scripts/quality-check.cjs`）が
すべてのテストを走らせ、落ちれば push できない。

実装はテストを先に書いて進める（test-driven-development）。

## 2. 確かめる観点

機能ごとに、次の 6 つの観点で「期待の一覧」を `features/` の各文書に日本語で書く。実装計画はその一覧からテストを起こす。

| 観点 | 問い | 例 |
| --- | --- | --- |
| 1. 正常系 | 仕様どおりに動くか | 本文を送ると投稿が作られ、タイムラインの先頭に出る |
| 2. 入力の境界 | 境目の値で正しく受け付け・拒否するか | 280 文字は通り、281 文字は 422。画像 4 枚は通り、5 枚は 422 |
| 3. 権限 | 許されない人を止めるか | 未ログインは 401。他人の投稿を編集・削除すると 403 で、何も変わらない |
| 4. 異常系 | 失敗したときに壊れないか | S3 への保存が途中で失敗したら、投稿は作られず、上げた画像も消える |
| 5. 重複と一意性 | 二重に起きないか | 同じ投稿に 2 回いいねしても 1 件のまま。同じユーザー名で 2 回登録すると 409 |
| 6. 並び順とページング | 一覧が正しい順で、欠けも重複もないか | 新しい順に 20 件。カーソルで続きを取ると、次の 20 件が重複なく返る |

多くの不具合は 2・3・4 に潜む。正常系だけで満足しない。

## 3. 層ごとの道具

同じ期待でも、確かめる場所によって速さと確からしさが変わる。どの期待をどの層で確かめるかは、実装計画で決める。

### backend

| 層 | 何を確かめるか | 道具 | DB |
| --- | --- | --- | --- |
| サービス | 認可の判定、検証、カーソルの扱い、S3 の失敗時の後始末 | JUnit 5 ＋ Mockito。Mapper と `ImageStorage` は代役 | 要らない |
| Web 層 | 各 API のステータスと Problem Details の形。401・403・422 の変換。JSON の入出力 | `@WebMvcTest` ＋ `MockMvc`。サービスは `@MockitoBean`。Spring Security の設定を読み込む | 要らない |
| Mapper | SQL が意図どおりの行を返すこと。一意制約、連鎖削除、カーソルの絞り込み | `@SpringBootTest` ＋ `@Transactional`。テスト用の DB `raise_timeline_test`（`db` サービスの初期化スクリプトが作り、`DB_URL_TEST` で渡す。テストでは `src/test/resources/application-test.properties` と `@ActiveProfiles("test")` で `spring.datasource.url=${DB_URL_TEST}` だけを上書きする。本体の `application.properties` と同じ名前のファイルをテスト側に置くと、本体の設定がまるごと読まれなくなるので置かない）に対して実行し、各テストの終わりに巻き戻す。Flyway が先にスキーマを作る。開発用の DB とは分けるので、手動確認で作った行の影響を受けず、「0 件なら空」「20 件ちょうどなら null」のような全件を前提にした期待も成り立つ | 要る（コンテナの中で走る） |
| 認証 | トークンの発行と検証、期限切れ、リフレッシュトークンの差し替えとログアウト後の拒否 | 上の層にまたがる | 一部要る |
| ログ | 要求ログの項目が揃うこと、500 で ERROR が 1 回だけ出ること、全項目を載せた 1 行が JSON として読めること（[logging-design.md](logging-design.md) の 12 章） | `OutputCaptureExtension` で標準出力を捕まえ、1 行ずつ JSON として読む | 要らない |
| 全体 | アプリが起動し、`GET /api/health` が 200 を返す | `@SpringBootTest` | 要る（テスト用の DB） |

- `HealthCheckControllerTest` が Web 層の、`RaiseTimelineApplicationTests` が全体の雛形
- 品質チェックはコンテナの中で `./gradlew check` を走らせるので、Mapper のテストは `db` サービスに届く。CI（GitHub Actions）はビルドだけで、テストは走らせない

### frontend

| 層 | 何を確かめるか | 道具 |
| --- | --- | --- |
| 部品 | 投稿カードの表示（編集済みの印、相対時刻）、フォームの検証と誤りの表示、無限スクロール一覧の状態（読み込み中・終端・再試行） | Vitest ＋ Testing Library |
| 通信 | API クライアントが 401 で更新を 1 回試してやり直すこと、Problem Details を `ApiError` に変換すること | `fetch` を `vi.fn` で代役にする |
| 画面遷移 | 未ログインで保護された画面を開くとログインへ移り、ログイン後に戻ること | React Router の `MemoryRouter` |
| hook | TanStack Query の hook が API の応答を一覧に変換すること | `QueryClientProvider` で包み、`fetch` を代役にする |

- `App.test.tsx` が雛形
- ブラウザの自動操作（E2E）は入れない。手動確認で代える

### 自動化しないもの

| 対象 | 確かめ方 |
| --- | --- |
| 本物の S3 への保存と削除 | ローカルで画面から投稿し、開発用バケットを見る |
| nginx の設定、本番用 Dockerfile、AWS の構成 | 本番構築の Issue で、実際に動かして完了条件を確かめる |
| 見た目、スマホ幅の表示 | ブラウザで確かめる |

機能ごとの文書に「手動確認の手順」を書き、PR の前に通す。

## 4. 代役（テストダブル）の使い分け

| 代役 | 作り方 | 向く場面 |
| --- | --- | --- |
| Mockito の代役 | `@MockitoBean` や `mock()`。「呼ばれたらこれを返せ」と指示する。呼ばれた回数や引数を確かめられる | Web 層のテストで、サービスや Mapper の振る舞いを固定する |
| 手書きのメモリ上の代役 | `InMemoryImageStorage` のように、インターフェースを `Map` で実装する | サービス層のテストで、「上げた画像が消されたか」のように、呼び出しの結果として残る状態を確かめる |

どちらも本物の S3 にもディスクにも書かない。テストが終われば何も残らない。本物の S3 に書く `S3ImageStorage` は数十行の薄い部品にとどめ、手動確認で担保する。

## 5. テストデータ

- Mapper のテストは、テストの中で必要な行を作る。共通の初期データ（フィクスチャ）は持たない
- 画像は数バイトの偽のデータ（JPEG のマジックナンバーだけを持つ配列）を使う
- 日時に依存するテストは、`Clock` を注入して固定する
- 利用者名とメールアドレスは、テストごとに乱数を含めて作る（他のテストや手動確認の行とぶつからない）

## 6. 命名と置き場

- backend: 本体と同じパッケージ構成で `src/test/java` に置く。クラス名は `<対象>Test`。`@DisplayName` に日本語で期待を書く（既存のテストと同じ）
- frontend: 対象のファイルの隣に `<対象>.test.tsx`。`describe` と `it` の文言は日本語

## 7. 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| E2E テスト（Playwright など）を自動化に入れる | 速さと安定性の割に手間が大きい。この規模なら手動確認で足りる |
| S3 のテストに S3Mock のコンテナを足す | 品質チェックはコンテナの中で走り、Docker を起動できない。Compose にサービスを足せば可能だが、まずは代役で十分 |
| 結合テストを開発用の DB に対して走らせる | 手動確認で作った行が残っていると、全件を前提にした期待が落ちる。テスト用の DB を分けるほうが単純 |
| Mapper のテストを H2 など別の DB で行う | PostgreSQL 固有の機能（`uuidv7()`、式インデックス、`ILIKE`）を使うので、本物でないと確かめられない |
