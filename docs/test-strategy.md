# テスト方針

- 日付: 2026-10-06

## 1. 考え方

テストは「この入力・この状態なら、プログラムはこう動くはず」という期待をコードとして書き、自動で実行するもの。
機能が増えるほど人が手で全部を確かめるのは無理になるので、機械に確かめさせる。push のたびに品質チェック（`scripts/quality-check.cjs`）が
すべてのテストを走らせ、落ちれば push できない。

実装はテストを先に書いて進める（test-driven-development）。

## 2. 確かめる観点

機能ごとに、次の 6 つの観点で「期待の一覧」を `features/` の各文書に日本語で書く。実装計画はその一覧からテストを起こす。

| 観点 | 問い | 例 |
| --- | --- | --- |
| 1. 正常系 | 仕様どおりに動くか | 本文を送ると投稿が作られ、タイムラインの先頭に出る |
| 2. 入力の境界 | 境目の値で正しく受け付け・拒否するか | 280 文字は通り、281 文字は 422。画像 4 枚は通り、5 枚は 422 |
| 3. 権限 | 許されない人を止めるか | 未ログインは 401。他人の投稿を編集・削除すると 403 で、何も変わらない |
| 4. 異常系 | 失敗したときに壊れないか | S3 への保存が途中で失敗したら、投稿は作られず、上げた画像も消える |
| 5. 重複と一意性 | 二重に起きないか | 同じ投稿に 2 回いいねしても 1 件のまま。同じユーザー名で 2 回登録すると 409 |
| 6. 並び順とページング | 一覧が正しい順で、欠けも重複もないか | 新しい順に 20 件。カーソルで続きを取ると、次の 20 件が重複なく返る |

多くの不具合は 2・3・4 に潜む。正常系だけで満足しない。

### 壊し方の一覧

期待一覧は、設計を読みながら書くと「設計どおりに動くか」の確認に寄る。異常系は「このアプリはどうやったら壊れるか」から考える。
機能の期待一覧と実装計画のテストを書くとき、次の一覧を上から当て、当たるものを期待にする。期待は 6 観点の見出しの下に書き、壊し方ごとの見出しは作らない。

- **利用者の操作で 500 を起こせたら不具合。** 500 は想定外の例外で、本番では ERROR が 1 件でもアラームが鳴り、メールが届く（[logging-design.md](logging-design.md) の 9 章）。入力で 500 を起こし続けられると、アラームが鳴ったままになり、本物の障害に気づけなくなる
- **設計で決めた守りは、破ろうとする側から確かめる。** 「正しい戻り先に戻る」だけでなく「外部サイトを指定されても飛ばない」を書く

| 壊し方 | このアプリでの例 | 期待 |
| --- | --- | --- |
| 形の壊れた要求 | JSON が壊れている、型が違う、id や cursor が UUID でない、multipart の部品が足りない | 400 か 422。500 にならない |
| 文字の端 | 空白だけ、NUL 文字、上限ちょうどと 1 つ超え、改行、絵文字、HTML やスクリプト、検索の `%` `_` `\` | 422、または文字として扱う |
| 消えた相手 | 操作の直前に投稿が消された、相手や自分が退会した、続きの目印（cursor）の投稿が消された | 404 か 401。続きの読み込みは欠けも重複も無く続く |
| 同時の操作 | 二重送信、同時の登録・いいね・フォロー、リフレッシュトークンの同時の更新 | 1 件だけ成立し、残りは決めた応答 |
| 外の失敗 | DB や S3 に届かない、S3 が途中で失敗する、通信が切れる、本文が JSON でない応答（nginx の 413・429） | 決めた応答になり、データや画像が半端に残らない。画面は入力を消さない |
| 悪意 | 他人の資源の id、改ざんしたトークン（署名違い、署名の方式 `none`）、外部サイトへの戻り先、`javascript:` の URL、拡張子を偽った画像、壊れた JPEG | 止める |
| 漏れ（応答） | エラーの本文、他人のプロフィールの応答 | 内部の情報（例外の文言、SQL、スタックトレース）と、パスワード・トークン・メールアドレスが出ない |
| 漏れ（ログ） | ログの行 | パスワードとトークンは DEBUG を含むどの行にも出ない。メールアドレスは INFO 以上の行に出ない（例外は、ローカルの既定の DEBUG で出る SQL の引数と、想定外の例外の文言。[logging-design.md](logging-design.md) 5 章）。例外の文言とスタックトレースは、例外を付けると決めた行（3 章の表の ERROR `http.request.failed` と WARN `health.db_unreachable`）にだけ出る |

## 3. 層ごとの道具

同じ期待でも、確かめる場所によって速さと確からしさが変わる。どの期待をどの層で確かめるかは、実装計画で決める。

### backend

| 層 | 何を確かめるか | 道具 | DB |
| --- | --- | --- | --- |
| サービス | 認可の判定、検証、カーソルの扱い、S3 の失敗時の後始末 | JUnit 5 ＋ Mockito。Mapper と `ImageStorage` は代役 | 要らない |
| Web 層 | 各 API のステータスと Problem Details の形。401・403・422 の変換。JSON の入出力 | `@WebMvcTest` ＋ `MockMvc`。サービスは `@MockitoBean`。Spring Security の設定を読み込む | 要らない |
| Mapper | SQL が意図どおりの行を返すこと。一意制約、連鎖削除、カーソルの絞り込み | `@SpringBootTest` ＋ `@Transactional`。テスト用の DB `raise_timeline_test`（`db` サービスの初期化スクリプトが作り、`DB_URL_TEST` で渡す。テストでは `src/test/resources/application-test.properties` と `@ActiveProfiles("test")` で `spring.datasource.url=${DB_URL_TEST}` だけを上書きする。本体の `application.properties` と同じ名前のファイルをテスト側に置くと、本体の設定がまるごと読まれなくなるので置かない）に対して実行し、各テストの終わりに巻き戻す。Flyway が先にスキーマを作る。開発用の DB とは分けるので、手動確認で作った行の影響を受けず、「0 件なら空」「20 件ちょうどなら null」のような全件を前提にした期待も成り立つ | 要る（コンテナの中で走る） |
| 認証 | トークンの発行と検証、期限切れ、リフレッシュトークンの差し替えとログアウト後の拒否 | 上の層にまたがる | 一部要る |
| ログ | 要求ログの項目が揃うこと、500 で ERROR が 1 回だけ出ること、全項目を載せた 1 行が JSON として読めること（[logging-design.md](logging-design.md) の 12 章） | `OutputCaptureExtension` で標準出力を捕まえ、1 行ずつ JSON として読む | 要らない |
| 全体 | アプリが起動し、`GET /api/health` が 200 を返す | `@SpringBootTest` | 要る（テスト用の DB） |

- `HealthCheckControllerTest` が Web 層の、`RaiseTimelineApplicationTests` が全体の雛形
- 品質チェックはコンテナの中で `./gradlew check` を走らせるので、Mapper のテストは `db` サービスに届く。CI（GitHub Actions）はビルドだけで、テストは走らせない

### frontend

| 層 | 何を確かめるか | 道具 |
| --- | --- | --- |
| 部品 | 投稿カードの表示（編集済みの印、相対時刻、本文の URL のうち `http://` と `https://` で始まるものだけがリンクになること）、フォームの検証と誤りの表示、無限スクロール一覧の状態（読み込み中・終端・再試行）、描画中の例外で ErrorBoundary の画面が出ること、500 の通知に requestId が全桁出ること | Vitest ＋ Testing Library |
| 通信 | API クライアントが 401 で更新を 1 回試してやり直すこと、Problem Details を `ApiError` に変換すること、本文が JSON でない応答（nginx の 413・429 の HTML）と通信の失敗も `code` が null の `ApiError` にすること | `fetch` を `vi.fn` で代役にする |
| 画面遷移 | 未ログインで保護された画面を開くとログインへ移り、ログイン後に戻ること。戻り先 `next` に外部サイト（`//` や `/\` で始まる値、`https://` で始まる値、タブを混ぜた値）を渡されても `/` へ移ること。存在しない URL で「ページが見つかりません」の画面が出ること | React Router の `MemoryRouter` |
| hook | TanStack Query の hook が API の応答を一覧に変換すること、ログアウトでキャッシュが空になること | `QueryClientProvider` で包み、`fetch` を代役にする |

- `App.test.tsx` が雛形
- ブラウザの自動操作（E2E）は入れない。手動確認で代える
- 画面の検証は使い勝手のためで、最終判断はサーバー。画面のテストは代表的な境界（上限ちょうどと 1 つ超え）だけにし、サーバーの規則をすべて繰り返さない

### 自動化しないもの

| 対象 | 確かめ方 |
| --- | --- |
| 本物の S3 への保存と削除 | ローカルで画面から投稿し、開発用バケットを見る |
| nginx の設定、本番用 Dockerfile、AWS の構成 | 本番構築の Issue で、実際に動かして完了条件を確かめる |
| 見た目、スマホ幅の表示 | ブラウザで確かめる |

機能ごとの文書に「手動確認の手順」を書き、PR の前に通す。

## 4. 代役（テストダブル）の使い分け

| 代役 | 作り方 | 向く場面 |
| --- | --- | --- |
| Mockito の代役 | `@MockitoBean` や `mock()`。「呼ばれたらこれを返せ」と指示する。呼ばれた回数や引数を確かめられる | Web 層のテストで、サービスや Mapper の振る舞いを固定する |
| 手書きのメモリ上の代役 | `InMemoryImageStorage` のように、インターフェースを `Map` で実装する | サービス層のテストで、「上げた画像が消されたか」のように、呼び出しの結果として残る状態を確かめる |

どちらも本物の S3 にもディスクにも書かない。テストが終われば何も残らない。本物の S3 に書く `S3ImageStorage` は数十行の薄い部品にとどめ、手動確認で担保する。

## 5. テストデータ

- Mapper のテストは、テストの中で必要な行を作る。共通の初期データ（フィクスチャ）は持たない
- PNG・GIF・WebP の画像は、先頭のバイト（マジックナンバー）だけを持つ数バイトの偽のデータでよい。サーバーは形式の判定にしか中身を読まないため
- JPEG は位置情報を取り除く処理が中身を解析するので、テストの中で `ImageIO` を使って作った小さな本物の画像を使う。位置情報付きの JPEG は、それに Commons Imaging で GPS の情報を書き足して作る。マジックナンバーだけの偽の JPEG は「読み取れない JPEG」（422）の期待に使う
- 日時に依存するテストは、`Clock` を注入して固定する
- 利用者名とメールアドレスは、テストごとに乱数を含めて作る（他のテストや手動確認の行とぶつからない）
- NUL 文字の期待は、文字列の途中と末尾の両方に置いて確かめる（末尾は前後の空白の除去で消えやすい）。JSON では `\u0000` のエスケープで送る。生の NUL のバイトは JSON として不正で、400 になる

## 6. 命名と置き場

- backend: 本体と同じパッケージ構成で `src/test/java` に置く。クラス名は `<対象>Test`。`@DisplayName` に日本語で期待を書く（既存のテストと同じ）
- frontend: 対象のファイルの隣に `<対象>.test.tsx`。`describe` と `it` の文言は日本語

## 7. 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| E2E テスト（Playwright など）を自動化に入れる | 速さと安定性の割に手間が大きい。この規模なら手動確認で足りる |
| S3 のテストに S3Mock のコンテナを足す | 品質チェックはコンテナの中で走り、Docker を起動できない。Compose にサービスを足せば可能だが、まずは代役で十分 |
| 結合テストを開発用の DB に対して走らせる | 手動確認で作った行が残っていると、全件を前提にした期待が落ちる。テスト用の DB を分けるほうが単純 |
| Mapper のテストを H2（Java の中で動く軽い DB）で行う | テーブルの定義がそのままでは通らない。H2 のインデックスは列しか指定できず、`lower(username)` の式インデックス（大文字小文字を区別しない一意性）を作れない。`uuidv7()` も H2 では名前が違う（`RANDOM_UUID(7)`）。H2 用のマイグレーションを別に持つと、テストする表と本番の表が別物になり、確かめたい一意性を本番と違う仕組みでしか確かめられない |
| Testcontainers でテストのたびに PostgreSQL のコンテナを立てる | テストは backend コンテナの中で走り、その中からは Docker を操作できない。操作させるにはホストの Docker の操作口（`docker.sock`）を渡す必要があり、コンテナにホストの管理者権限を渡すのとほぼ同じになる。ホストで走らせるには、ホストに Java が要る |
| 組み込みの PostgreSQL（embedded-postgres など）をテストの中で起動する | PostgreSQL は管理者（root）では起動を拒むが、backend コンテナは root で動いている。一般の利用者で動かすように作り替えると、root 所有のボリュームの扱いまで変わる |
| スナップショットテスト（画面の出力を丸ごと保存して比べる） | 見た目を少し変えるたびに落ち、不具合は見つけにくい |
| カバレッジの数値目標 | 数字を満たすためのテストが増えやすい。観点と壊し方の一覧で抜けを探すほうが効く |
