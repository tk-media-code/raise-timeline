# 要件定義書

- 日付: 2026-10-06

## 1. 目的

- プログラミングスクールの学習課題として、X（旧 Twitter）を模した SNS アプリを作る
- 学習用だが本番に出し、複数の人が実際に使う。認証・認可・入力検証・エラー処理は実際に使える水準にする
- 要件定義と設計を先に文書に揃え、機能ごとに Issue を切って実装する

既に用意してある土台（React 19 / TypeScript / Vite / Tailwind CSS / React Router と、Java 25 / Spring Boot 4 / MyBatis / Flyway / PostgreSQL 18）の中で作る。土台の設計は [superpowers/specs/](superpowers/specs/) にある。

## 2. 利用者と規模

| 項目 | 想定 |
| --- | --- |
| 利用者 | スクールの仲間が中心。URL を知っていれば誰でも登録できる |
| 人数 | 数十〜数百人 |
| 投稿 | 数万件まで |
| 画像 | 数 GB まで |
| 閲覧 | すべてログインが要る。未ログインで開けるのは登録とログインの画面だけ |
| 画像の閲覧 | 例外として、投稿画像とアイコンは推測できない URL（S3 の公開 URL）を知っていれば未ログインでも見られる。画面とタイムラインはログインが要る。[image-storage-design.md](image-storage-design.md) |

## 3. 機能要件

### 3.1 アカウント（登録・ログイン・ログアウト・退会）

| 項目 | 要件 |
| --- | --- |
| 登録の入力 | ユーザー名、表示名、メールアドレス、パスワード |
| ユーザー名 | 英数字と `_` の 3〜20 文字。大文字小文字を区別せず一意。**登録後は変えられない** |
| 表示名 | 1〜50 文字 |
| メールアドレス | 254 文字以内の形式。大文字小文字を区別せず一意。登録後は変えられない |
| パスワード | 8〜72 文字の半角英数字と記号 |
| メール確認 | しない。登録した瞬間から使える |
| ログイン | メールアドレスとパスワード |
| ログインの持続 | ブラウザを閉じても続く。使い続けている限り切れない。30 日間使わなければ再ログイン |
| ログアウト | サーバー側でも無効にする。ログアウト後は古いトークンで続きを使えない |
| 退会 | プロフィール編集画面から退会できる。パスワードを入力して確定する。利用者の投稿・画像・コメント・いいね・フォロー関係がすべて消え、元に戻せない。ユーザー名とメールアドレスは再び登録に使える |

### 3.2 プロフィール

| 項目 | 要件 |
| --- | --- |
| 表示 | アイコン、表示名、ユーザー名、自己紹介、フォロー中の数、フォロワーの数、登録日、その人の投稿一覧 |
| 更新できるもの | 表示名、自己紹介（0〜160 文字）、アイコン画像 |
| アイコン | 1 枚。JPEG / PNG / GIF / WebP、2 MB まで。差し替えると前の画像は消す。未設定なら表示名の頭文字を出す |
| 更新できないもの | ユーザー名、メールアドレス。パスワードの変更は範囲外 |

### 3.3 投稿

| 項目 | 要件 |
| --- | --- |
| 本文 | 0〜280 文字。画像が無いときは本文が必須（本文も画像も無い投稿は作れない） |
| 画像 | 0〜4 枚。JPEG / PNG / GIF / WebP。1 枚 5 MB まで |
| 位置情報 | JPEG に入っている撮影地の GPS 座標（Exif の GPS IFD と XMP）は、保存の前に取り除く。写真の向き（Orientation）などの他の情報は残す。PNG / GIF / WebP は対象外 |
| 編集 | 本文だけ編集できる。画像は変えられない（変えたければ削除して投稿し直す）。編集済みの印を出す。履歴は持たない |
| 削除 | 投稿した本人だけ。いいね・コメント・画像も一緒に消える |
| 詳細画面 | 投稿 1 件と、そのコメント一覧 |
| 画像の表示 | 押すと同じ画面の上にビューアを重ねて原寸で表示する。複数枚は前後に移れる |

### 3.4 タイムライン

| 項目 | 要件 |
| --- | --- |
| タブ | 「フォロー中」は自分とフォローしている人の投稿。「すべて」は全員の投稿。どちらも新しい順 |
| 読み込み | 20 件ずつ。末尾まで見ると次の 20 件を自動で読む（無限スクロール）。無くなるまで繰り返す |
| 1 件の表示 | アイコン、表示名、ユーザー名、相対時刻、本文、画像、いいね数とボタン、コメント数 |
| 時刻 | 24 時間以内は「3 分前」「5 時間前」の相対表示。24 時間を過ぎたら「10月5日」、年が変わっていれば「2025年10月5日」。マウスを載せると絶対時刻（日本時間） |

### 3.5 いいね

| 項目 | 要件 |
| --- | --- |
| 規則 | 投稿に対して 1 人 1 回。付ける・外すができる。自分の投稿にも付けられる |
| 表示 | いいね数と、自分が付けたかどうか |
| 一覧 | 投稿にいいねした人の一覧を、新しい順に 20 件ずつ見られる |

### 3.6 コメント

| 項目 | 要件 |
| --- | --- |
| 内容 | テキストのみ 1〜280 文字。画像なし。コメントへの返信（入れ子）なし。コメントへのいいねなし |
| 操作 | 書いた本人だけ削除できる。編集はなし。投稿の持ち主でも他人のコメントは消せない |
| 表示 | 投稿詳細に新しい順。20 件ずつの無限スクロール。投稿した直後に自分のコメントが先頭に出る |

### 3.7 フォロー

| 項目 | 要件 |
| --- | --- |
| 規則 | 承認なしで即フォロー。自分自身はフォローできない。解除できる |
| 一覧 | プロフィールから、フォロー中の一覧とフォロワーの一覧を見られる。新しい順に 20 件ずつ |
| 表示 | プロフィールにフォロー中の数とフォロワーの数。ユーザーの一覧にはフォローボタン |

### 3.8 ユーザー検索

| 項目 | 要件 |
| --- | --- |
| 対象 | ユーザー名と表示名の部分一致。大文字小文字を区別しない |
| 実行 | 入力が止まって 400 ミリ秒後に自動で検索する。Enter で即時。検索ボタンは置かない。入力中は履歴を積まない |
| 結果 | アイコン、表示名、ユーザー名、自己紹介、フォローボタン。20 件ずつ |
| 投稿の検索 | 範囲外 |

### 3.9 文字数の数え方

文字数は Unicode のコードポイント数で数える。サーバーと画面で同じ数え方にし、画面では入力中に残り文字数を出す。

## 4. 非機能要件

| 区分 | 要件 |
| --- | --- |
| 性能 | 通常の操作は 1 秒以内に応答する。一覧は 20 件ずつ返す |
| 規模 | 利用者数百人、投稿数万件、画像数 GB まで性能を落とさない |
| 可用性 | 単一の EC2 と単一 AZ の RDS。計画停止を許容する。RDS の自動バックアップを 7 日分残す |
| 安全 | 通信は HTTPS のみ。パスワードは BCrypt で保存。トークンはサーバー側で無効化できる。入力はサーバーで検証する。秘密情報はリポジトリに置かない |
| 対応環境 | 最新の Chrome / Safari / Firefox / Edge。スマホ幅（360px〜）から PC 幅まで |
| 言語と時刻 | UI は日本語のみ。日時は UTC で保存し、日本時間で表示する |
| 運用 | アプリと nginx のログを 1 行 1 JSON で CloudWatch Logs に集め、リクエストごとの ID で追える。ERROR、5xx の急増、ログイン失敗の急増、ヘルスチェックの失敗はメールで通知する（[logging-design.md](logging-design.md)） |
| 費用 | 本番は月 $70 前後を上限の目安にする（公開 IPv4 アドレスの料金を含む） |
| 保守 | すべての変更は Issue → ブランチ → PR。push 時に静的解析とテストが自動で走る |

## 5. 範囲外（今回は作らない）

通知、リポスト・引用、ハッシュタグ、DM、ブックマーク、投稿の検索、鍵アカウント、ブロック・ミュート、管理者機能、メール確認、パスワードの変更・再設定、ユーザー名とメールアドレスの変更、動画の投稿、コメントへの返信、コメントへのいいね、コメントの編集、X の右カラム（トレンド、おすすめ）、ブラウザで起きた問題のサーバーへの報告、ログのダッシュボード、退会の取り消し・猶予期間・退会理由の入力・メールでの確認。

必要になったら、それぞれを新しい Issue として起こす。

## 6. 実装の順序

1 Issue ＝ 1 ブランチ ＝ 1 PR とし、それぞれ `writing-plans` で計画を書いてから着手する。前の Issue の成果だけで次が動くように並べている。

| 順 | Issue | 中身 | 主な設計書 |
| --- | --- | --- | --- |
| 0 | 要件定義書と設計書を整備する | この文書一式 | すべて |
| 1 | ログの基盤を作る | JSON の構造化ログ、requestId と要求ログ、Problem Details と例外ハンドラの共通部分、`/api/health` への移動、README のログの読み方 | [logging-design.md](logging-design.md)、[error-handling-design.md](error-handling-design.md) |
| 2 | 認証の基盤を作る | Spring Security ＋ JWT、`users` と `refresh_tokens`、Spring Security のエラー応答と利用者 id のログ、Vite の proxy、フロントの API クライアント・認証状態・共通レイアウト・登録とログインの画面 | [features/auth.md](features/auth.md) と横断文書 |
| 3 | 投稿とタイムラインを作る | テキストのみの投稿、編集、削除、投稿詳細、タイムラインの「すべて」、無限スクロールの部品 | [features/post.md](features/post.md)、[features/timeline.md](features/timeline.md) |
| 4 | プロフィールを作る | 表示、編集（表示名と自己紹介）、その人の投稿一覧 | [features/profile.md](features/profile.md) |
| 5 | 画像を扱う | S3 連携、投稿画像、アイコン、画像ビューア | [image-storage-design.md](image-storage-design.md)、post.md、profile.md |
| 6 | 退会を作る | `DELETE /api/users/me`、連鎖削除、S3 の画像の削除、認証時の存在確認、編集画面の退会の節 | [features/auth.md](features/auth.md) |
| 7 | いいねを作る | いいねの付け外し、いいねした人の一覧 | [features/like.md](features/like.md) |
| 8 | コメントを作る | 投稿と削除、一覧 | [features/comment.md](features/comment.md) |
| 9 | フォローを作る | フォローと解除、フォロワーとフォロー中の一覧、タイムラインの「フォロー中」 | [features/follow.md](features/follow.md)、timeline.md |
| 10 | ユーザー検索を作る | 検索画面と API | [features/user-search.md](features/user-search.md) |
| 11 | 本番環境に出す | 本番用 Dockerfile と nginx、本番用 compose、AWS の構築手順、デプロイ手順 | [architecture.md](architecture.md) |

画像を 5 番目にしたのは、投稿とプロフィールの両方に関わるので、両方のテキスト版が揃ってからまとめて入れる方が小さく済むため。退会を 6 番目にしたのは、S3 の画像の削除が要るため。

### Issue ごとの仮の振る舞い

前の Issue の時点では、後の Issue が作るテーブルがまだ無い。そのあいだの振る舞いを決めておく。機能別文書のテストの期待一覧は、その機能の Issue で確かめる。

| Issue | 仮の振る舞い |
| --- | --- |
| 3〜6（投稿、プロフィール、画像、退会） | Post の `likeCount` と `commentCount` は 0、`likedByMe` は false を返す。`likes` と `comments` ができたら数えた値に変える |
| 3〜4 | 投稿の `images` は `[]`、`author.avatarUrl` は null を返す。`POST /api/posts` は最初から multipart で受け、`images` の部品が 1 つでもあれば、本文の検査より先に 503 `IMAGE_STORAGE_UNAVAILABLE`（「画像の保存が設定されていません」）を返す。画面のいいね数とコメント数は押せない表示にする（`role="img"`、名前は「いいね 0 件」「コメント 0 件」）。画像（Issue 5）が `images` とアイコンを足し、いいね（Issue 7）とコメント（Issue 8）が値と操作を足す。Issue 7 では同じ名前のボタンに替える。画像付きの投稿を黙って捨てると、画像が付いたと思った利用者に嘘をつく。multipart にしておくのは、API の形を Issue 5 で変えないため |
| 3〜8 | ホームは「すべて」のタブだけ。「フォロー中」のタブと `GET /api/timeline/following` は Issue 9 で足す。それまでホームの既定は「すべて」で、URL の `tab` はまだ読まない（Issue 9 で足す） |
| 4〜8（プロフィール） | `followersCount` と `followingCount` は 0、`isFollowing` は false を返す。`follows` ができたら数えた値に変える |
| 3 | 「投稿を削除するといいねとコメントも消える」は、Issue 7 と 8 でそれぞれ確かめる |
| 6（退会） | いいね・コメント・フォローの表はまだ無いので、退会で消えるのは利用者・投稿・画像・リフレッシュトークンだけ。後の Issue で表を作るときに `ON DELETE CASCADE` を付けるので、自動的に対象になる。「いいね・コメント・フォローも消える」は Issue 7〜9 でそれぞれ確かめる |
| 2 | テスト用の DB（[test-strategy.md](test-strategy.md) の 3 章）はこの Issue で用意する |
| 5 | JPEG の GPS 情報の除去もこの Issue で入れる |
| 7〜8（いいねした人の一覧） | `isFollowing` は false を返す。SQL の `EXISTS (SELECT 1 FROM follows ...)` は Issue 9 で足す |
| 4〜8 | プロフィールとユーザーカードのフォローボタンは出さない。Issue 9 で足す |

## 7. 決めたこと（人の判断）

| 論点 | 決定 | 採らなかった案 |
| --- | --- | --- |
| 設計書の読み手 | 講師への提出物でもあり、実装の拠り所でもある | どちらか一方 |
| タイムラインの中身 | 「フォロー中」と「すべて」の 2 タブ | フォロー中のみ／全体のみ |
| 公開範囲 | すべてログイン必須 | 閲覧は誰でも、操作はログイン必須 |
| 規模と登録 | 数十〜数百人。登録は誰でも | 招待制／数千人以上を見込む |
| 設計書の構成 | 横断文書＋機能別文書の二層 | 観点別の横断文書だけ／機能別フォルダに全部入れる |
| システムの組み方 | 同一オリジンのモノリス（nginx ＋ Spring Boot、[architecture.md](architecture.md) の案A） | フロントを S3 ＋ CloudFront に分離／jar に React を同梱 |
| ローカルの S3 | 本物の S3 の開発用バケットを使う | S3Mock／RustFS（MinIO の無償版は 2025 年 10 月に Docker イメージの配布をやめ、2026 年に開発を止めていた） |
| ユーザー名 | 登録後は変えない | 変更できるようにする |
| 削除の権限 | 投稿もコメントも書いた本人だけ | 投稿の持ち主も他人のコメントを消せる |
| いいねした人の一覧 | 作る | 範囲外にする |
| コメントの並び | 新しい順 | 古い順（投稿後に一覧を読み直す） |
| 画像の表示 | 同じ画面にモーダルのビューア | 別タブで原寸を開く |
| 認証の方式 | アクセストークン（メモリ）＋リフレッシュトークン（httpOnly Cookie） | アクセストークンだけ／アクセストークンを localStorage に置く |
| フロントの通信 | TanStack Query を足す | fetch と自作の hook だけ |
| テストの進め方 | 機能ごとに 6 観点の期待一覧を日本語で書き、どの層で確かめるかは実装計画で決める | 層ごとの技術的な方針だけを示す |
| 退会（プロトタイプの確認で追加） | 入れる。パスワードを入力して確定し、内容はすべて消す | 範囲外のまま／内容を「削除されたユーザー」として残す |
| ユーザー検索の実行（同上） | 入力が止まって 400 ミリ秒後に自動で実行。Enter で即時 | 検索ボタンで実行 |
| PC の中央カラムの幅（同上） | 800px | 600px（X と同じ） |
| 画像の公開範囲 | 画像だけは、推測できない URL を知っていれば未ログインでも見られる（「すべてログイン必須」の例外） | 署名付き URL で画像もログイン必須にする |
| 写真の位置情報 | JPEG の GPS の情報を保存の前に取り除く（向きの情報は残す） | 範囲外にして、画面で注意を出す |
| 費用の目安 | 月 $70 前後（公開 IPv4 アドレスの料金を含む） | $50〜60 のままにして、本番構築で構成を見直す |
| ログの形式 | ローカルも本番も 1 行 1 JSON の ECS 形式（Spring Boot 組み込み）。項目名は ECS の辞書に合わせる | Logstash 形式／自作の整形器／ローカルだけ人向けのテキスト |
| 本番で問題に気づく仕組み | CloudWatch のメトリクスフィルタとアラーム、SNS のメール通知 | 通知を入れない／Lambda で Slack へ送る／外部の監視サービス |
| ブラウザで起きた問題の報告 | 範囲外。画面のエラー通知に requestId を添えるだけにする | ブラウザからサーバーへ報告する口を作る |
| ログ基盤の置き場 | 認証より先に独立した Issue「ログの基盤を作る」にする | 認証の Issue に含める |
| ローカルのログの水準 | 既定で DEBUG（SQL とその引数も出る）。本番は INFO | ローカルも INFO にし、必要なときだけ DEBUG に切り替える |
| AI への「まずログを読む」指示 | 原則はハーネスが全リポジトリに配り、ログの読み方はこのリポジトリのルールに置く | このリポジトリのルールにだけ置く |
| 壊れた入力の扱い | NUL 文字や対になっていないサロゲートを含む文字列と、読み取れない JPEG は 422 で弾く。利用者の操作で 500 を起こせたら不具合とする | そのまま通して 500 にする／壊れた JPEG は位置情報を消さずに保存する |
| 異常系のテスト | 全機能に当てる「壊し方の一覧」をテスト方針に置き、設計で決めた守りは破る側から確かめる | 機能ごとに思いついた異常系だけを書く |
| 別のタブへのログイン・ログアウトの通知（Issue 3 の作業中に追加） | ログイン・登録・ログアウトの後に、同じブラウザの他のタブへ BroadcastChannel で知らせる。受け取ったタブは持っているトークン・利用者・キャッシュを捨てて取り直す。結果として、1 つのブラウザでログインしているのは最後にログインした 1 人だけになる。共用の端末で、閉じ忘れたタブから前の人として投稿できてしまうのを防ぐ | 知らせない（リフレッシュ Cookie は全タブで共有だが、アクセストークンはタブごとのメモリにあるので、閉じ忘れたタブが最長 1 時間は前の人として動く） |
| 別のタブで利用者が替わったときの安全網（同上） | 更新で返った利用者が、そのタブが覚えている利用者と違えば、新しいトークンは使わず、期限切れと同じく未ログインにする。知らせを受け損ねたときでも、画面は X さんなのに Y さんとして投稿される食い違いを塞ぐ | 食い違いを見ずにそのまま受け入れる／サーバーでアクセストークンを無効にする（設計を大きく変えるわりに、この食い違いを直せない。理由は [auth-design.md](auth-design.md) の 9 章） |
