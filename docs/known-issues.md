## 使い方

- PR の「次の Issue 以降に回したもの」のうち、すぐ次の Issue で扱わないものは、その PR の中でこの文書にも足す。PR の本文にも、これまでどおり残す
- 節は、残す理由で分ける。**次の Issue で扱う**、**本番の構築で扱う**、**実機で確かめる**、**直さないと決めたもの**、**受け入れたこと**
- 片付いたら、その項目をこの文書から消す。消した理由は、片付けた PR に書く
- 「直さないと決めたもの」には、必ず理由を 1 文つける。理由が消えたら（起きる経路ができた、規模が変わった）、項目を見直す

## 本番の構築で扱う

実装の順序 11「本番環境に出す」で行う。構成は [architecture.md](architecture.md) の 3 章。

- **回数の制限。** ログイン・登録・退会・ユーザー検索・更新（`/api/auth/refresh`）の API に、nginx の `limit_req` を掛ける。ログイン・登録・退会は 1 IP あたり毎分 20 回、バースト 20 から始める（[architecture.md](architecture.md) の 3 章「本番構築の前に決めること」と 6 章の総当たり対策）。検索の API の流量も同じ nginx で制限する。更新の口を足すのは、猶予の中では使用済みの同じ Cookie を繰り返し送るたびに 30 日有効の行が増える（掃除は未使用の行を消さない）ので、ログインしている人が `refresh_tokens` を太らせられるため
- **V6 より前の版のアプリへ戻すとき。** ローリングデプロイで前の版と並ぶ間も含め、`DELETE FROM refresh_tokens WHERE used_at IS NOT NULL` を流す。前の版は `used_at` を知らず、使用済みの行を未使用として 1 回使えてしまうため
- **本番で開発用の署名鍵を拒む。** `JWT_SECRET` は、ローカルでは `docker-compose.yml` に書いた開発専用の値で動く（[architecture.md](architecture.md) の 2 章）。本番で、この開発専用の値のまま起動したら、起動を失敗させる
- **pgjdbc の `logServerErrorDetail`。** 既定では、制約違反の例外のメッセージにサーバーが返した詳細（重複した値など）が入る。メールアドレスなどがログに出ないよう、本番でこの設定をどうするかを決める（[logging-design.md](logging-design.md) の 5 章の、書いてはいけない値）
- **退会のパスワード違いを見張るか。** 退会のパスワード違い（要求ログの `event.code="INVALID_PASSWORD"`）は出来事として残さない（[features/auth.md](features/auth.md) の 4 章）。総当たりの試みを見張る必要があるかを、メトリクスフィルタ（[logging-design.md](logging-design.md) の 9 章）と合わせて決める
- **検索語をアクセスログに残さない。** nginx の `$args` で、検索語（`q`）の値を伏せる（[logging-design.md](logging-design.md) の 13 章に引き継ぎ済み）

## 受け入れたこと

起きうると分かっていて、直すより受け入れる方がよいと決めたもの。

- 投稿のいいねの送信中に一覧が読み直され、その応答が最後の書き直しより後に届くと、古い状態が見えることがある。投稿の編集の応答が、送信中のいいねより古い状態を運ぶことも同じ。どちらも次の読み直しで直る
- 0 件の一覧を開き直したときに投稿が消えていると、「見つかりません」ではなく「再試行」が出る
- 投稿詳細を開いている間に、他の人が書いたコメントは、読み直すまで出ない
- 一覧の読み直しと ±1 が重なると、数が一瞬ずれることがある。次の読み直しで直る
- 相手のフォロワー数の ±1 と読み直しが重なると、数が一瞬ずれることがある
- 他の人がフォロー・解除したことによる数の変化は、読み直すまで出ない
- 通知が 2 つ重なったり 3 行に折り返したりすると、PC の下の余白（96px）を超えて、ページの最後の要素にかかることがある。通知を閉じれば押せる
- 一覧から消したあとのフォーカスは、別の画面へ移っていれば動かさない。ただし、同じ見出しが残ったまま一覧だけが入れ替わる移動（プロフィールからプロフィール、ホームのタブの切り替え）で、削除の通信中にフォーカスがすでに画面の先頭に落ちていた場合だけ、見出しへ移る。入力中のフォーカスを奪うことは無い
- 投稿は最大 5 MB × 4 枚で、画面では縮めずに送る。応答はサーバーが S3 へ上げ終えてから返るので、120 秒で送り切るには上りがおよそ 1.4 Mbps 以上要る。それより遅い回線では、画像の多い投稿が毎回「通信に失敗しました」になる（枚数を減らせば送れる）。本文の大きさに応じて待ち時間の上限を伸ばすかは、人の判断を待っている。直さない理由が決まったものではなく、判断までの間の既知の状態なので、この節に置く
