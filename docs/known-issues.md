# 残している課題

- 日付: 2026-10-11

いま分かっていて、まだ直していないことを 1 か所に集める。PR の本文に「次の Issue 以降に回したもの」として散らばると、後で拾われないため。

## 使い方

- PR の「次の Issue 以降に回したもの」のうち、すぐ次の Issue で扱わないものは、その PR の中でこの文書にも足す。PR の本文にも、これまでどおり残す
- 節は、残す理由で分ける。**次の Issue で扱う**、**本番の構築で扱う**、**実機で確かめる**、**直さないと決めたもの**、**受け入れたこと**
- 片付いたら、その項目をこの文書から消す。消した理由は、片付けた PR に書く
- 「直さないと決めたもの」には、必ず理由を 1 文つける。理由が消えたら（起きる経路ができた、規模が変わった）、項目を見直す

## 次の Issue で扱う

### ログインの更新が重なると、ログアウトになる

次の Issue「ログインの更新が重なってもログアウトしないようにする」で扱う。本番に出す前に行う（[requirements.md](requirements.md) の 6 章）。

**起き方。** リフレッシュトークンは、使うたびに新しいものへ差し替え、古いものは消す（使い捨て。[auth-design.md](auth-design.md) の 2 章）。そのため、更新が 1 回成功したあとに、同じ古いトークンで来た更新は 401 になる。401 になった画面は、ログアウト状態になる。

- 更新の応答が届く前にページが読み直されると、サーバーでは入れ替わったトークンを、画面が受け取れずに失う。次の更新は、消えた古いトークンを出して 401 になる。PR #30 の手動確認で、開発用の自動再起動と再読み込みが重なって実際に起きた
- ページの全読み込みを、ごく短い間隔（50 ミリ秒）で 2 回続けると、更新の要求が重なって片方が 401 になった（PR #42 の手動確認）
- 人の操作では起きにくいが、本番でもまれに起きうる。同じブラウザのタブの間は、Web Locks の鍵で更新を 1 本ずつに並べてある（[auth-design.md](auth-design.md) の 3 章）が、これらは実際に起きた

**検討する対策。** 直前のトークンを数秒だけ受け付ける。

**その危険。** 古いトークンを受け付ける数秒のあいだ、盗まれたトークンでも更新ができる。盗まれたトークンが使い捨てで無効になる、という守りが、その数秒だけ弱くなる。受け付ける秒数と、受け付けた後の扱い（使ったら元のトークンを無効にするか、など）は、次の Issue で決める。設計書（[auth-design.md](auth-design.md)）と DB（`refresh_tokens`）の変更が要る。

**関連して分かっていること。** 通信の待ち時間の上限で画面が打ち切った更新を、サーバーが完了させていることがある。そのときも使い捨てのトークンが消費されて、次の更新が 401 になる。上の対策の検討材料にする。

## 本番の構築で扱う

実装の順序 11「本番環境に出す」で行う。構成は [architecture.md](architecture.md) の 3 章。

- **回数の制限。** ログイン・登録・退会・ユーザー検索の API に、nginx の `limit_req` を掛ける。ログイン・登録・退会は 1 IP あたり毎分 20 回、バースト 20 から始める（[architecture.md](architecture.md) の 3 章「本番構築の前に決めること」と 6 章の総当たり対策）。検索の API の流量も同じ nginx で制限する
- **本番で開発用の署名鍵を拒む。** `JWT_SECRET` は、ローカルでは `docker-compose.yml` に書いた開発専用の値で動く（[architecture.md](architecture.md) の 2 章）。本番で、この開発専用の値のまま起動したら、起動を失敗させる
- **pgjdbc の `logServerErrorDetail`。** 既定では、制約違反の例外のメッセージにサーバーが返した詳細（重複した値など）が入る。メールアドレスなどがログに出ないよう、本番でこの設定をどうするかを決める（[logging-design.md](logging-design.md) の 5 章の、書いてはいけない値）
- **退会のパスワード違いを見張るか。** 退会のパスワード違い（要求ログの `event.code="INVALID_PASSWORD"`）は出来事として残さない（[features/auth.md](features/auth.md) の 4 章）。総当たりの試みを見張る必要があるかを、メトリクスフィルタ（[logging-design.md](logging-design.md) の 9 章）と合わせて決める
- **検索語をアクセスログに残さない。** nginx の `$args` で、検索語（`q`）の値を伏せる（[logging-design.md](logging-design.md) の 13 章に引き継ぎ済み）

## 実機で確かめる

開発の最後に、実機のスマホでまとめて確かめる。

- **スマホで撮った写真の位置情報。** 位置情報（Exif の GPS）が保存の前に消えるか。自作の JPEG では確かめた（[image-storage-design.md](image-storage-design.md) の 3 章）
- **スマホの日本語入力での自動検索。** Android の Gboard（英字入力）と、iOS の日本語入力。Gboard は英字でも変換のイベントで包むことがあり、その場合、自動検索が単語の確定まで待つ（[features/user-search.md](features/user-search.md)）
- **読み上げソフトで成功の通知が読まれるか。** 通知が重なったときに全部を読むかどうか（`aria-atomic`）も、そのときに判断する（[screen-design.md](screen-design.md) の 4 章の通知）

## 受け入れたこと

起きうると分かっていて、直すより受け入れる方がよいと決めたもの。

- 投稿のいいねの送信中に一覧が読み直され、その応答が最後の書き直しより後に届くと、古い状態が見えることがある。投稿の編集の応答が、送信中のいいねより古い状態を運ぶことも同じ。どちらも次の読み直しで直る
- 0 件の一覧を開き直したときに投稿が消えていると、「見つかりません」ではなく「再試行」が出る
- 投稿詳細を開いている間に、他の人が書いたコメントは、読み直すまで出ない
- 一覧の読み直しと ±1 が重なると、数が一瞬ずれることがある。次の読み直しで直る
- 相手のフォロワー数の ±1 と読み直しが重なると、数が一瞬ずれることがある
- 他の人がフォロー・解除したことによる数の変化は、読み直すまで出ない
- 通知が 2 つ重なったり 3 行に折り返したりすると、PC の下の余白（96px）を超えて、ページの最後の要素にかかることがある。通知を閉じれば押せる
- 一覧から消したあとのフォーカスは、別の画面へ移っていれば動かさない。ただし、プロフィールからプロフィールへ移ったとき（同じ部品が使い回され、見出しも使い回される）に、フォーカスがすでに画面の先頭に落ちていた場合だけ、移った先の見出しへ移る。入力中のフォーカスを奪うことは無い
