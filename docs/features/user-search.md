# ユーザー検索

- 日付: 2026-10-06
- 要件: [requirements.md](../requirements.md) の 3.8
- 設計: [api-conventions.md](../api-conventions.md)、[database-design.md](../database-design.md) の 4〜5 章
- Issue: 実装の順序の 10「ユーザー検索を作る」

## 1. 概要

ユーザー名と表示名の部分一致でユーザーを探す。大文字小文字を区別しない。結果からプロフィールへ移り、その場でフォローできる。

## 2. 画面 `/search`

| 要素 | 内容 |
| --- | --- |
| 見出し | 「検索」。スマホ幅では上部バーに同じ画面名が出るので、見た目では隠して読み上げ用に残す（ホームと同じ） |
| 検索欄 | 見出しの下。検索の欄（`<form role="search">` の中の `type="search"`）。見える文字（`placeholder`）は「ユーザー名か表示名で探す」、読み上げの名前（`aria-label`）は「ユーザー名か表示名」。上には固定しない。開いたときに自動でフォーカスしない（スマホで「戻る」で戻ったときにキーボードが勝手に開かないため）。検索ボタンは置かない |
| 検索のタイミング | 入力が変わるたびに 400 ミリ秒のタイマーを掛け直し、止まって 400 ミリ秒経つと自動で検索する。Enter を押すとタイマーを止めてすぐ検索する（あとからタイマーが 2 回目を起こさない）。日本語の変換中は検索しない（変換の開始でタイマーを止め、確定してから 400 ミリ秒を数える）。空にしたときも 400 ミリ秒後に初期状態に戻る |
| URL | 検索したとき（400 ミリ秒後か Enter）にだけ `?q=` を書き換える。履歴は置き換える（React Router なら `setSearchParams(..., { replace: true })`）。書くのは前後の空白を除いた語で、51 文字以上でも書く（リロードで同じ誤りが出る）。空なら `q` を消す。開いたときに `q` があればそれで検索する |
| 結果 | 一覧の名前は「検索結果」。ユーザーカードの無限スクロール（1 ページ 20 件）。自分も出るが、自分にはフォローボタンが出ない |
| 初期状態 | 「ユーザー名か表示名で探せます」 |
| 該当なし | 「該当するユーザーがいません」 |
| 誤り（画面） | 空や空白だけでは検索せず、初期状態に戻る。51 文字以上は、検索したときに欄の下へ「50 文字以内で入力してください」と出し、検索しない（1 文字ごとには出さない） |
| 誤り（サーバー） | API が 422 を返したら、その文言を欄の下に 51 文字以上と同じ形で出す。422 の `errors` が空なら、問題の `detail` を出す。一覧も「再試行」も出さない（再試行しても直らないため。URL を手で書き換えて NUL を入れた場合など）。通信の失敗と 500 は「再試行」を出す |

- ブラウザの「戻る」は、検索画面に来る前の画面に戻る。入力中の 1 文字ごとの履歴は残さない。リロードや URL の共有では `q` から復元する
- 応答が返る順番が入れ替わっても、古い検索の結果が新しい検索の結果を上書きしないようにする（最新の `q` の結果だけを表示する。TanStack Query ならクエリのキーに `q` を入れれば満たせる）
- 検索語が変わったら、前の結果はすぐ消して読み込み中の印を出す（前の結果を残さない）。どの語の結果か見分けがつかなくなるため
- 何を表示するかは、URL の `q` だけから決める。`q` が空（無い・空白だけ）なら初期状態、51 文字以上なら欄の下に誤り（一覧は出さず API も呼ばない）、それ以外は API を呼ぶ。欄の中身ではなく URL を見るので、リロード・URL の共有・「戻る」で同じ表示になる
- 検索画面にいるときに、左ナビ・下部タブの「検索」を押すと、欄が空になって初期状態に戻る。画面は、自分が行った URL の書き換え（履歴の状態に印を持たせた置き換え）と、外からの移動（リンク・戻る・進む）を見分け、外からの移動のときだけ欄を URL の語で作り直す。欄に `q` を毎回書き戻すと、入力中の末尾の空白（「ali 」）が消えて、続けて打った文字が前の語に付いてしまうため。作り直すとき、待っているタイマーも捨てるので、古い語が URL に書き戻されない
- 検索結果でフォローすると、ほかの一覧やプロフィールの同じ人のボタンもすぐ変わり、逆も同じ。404 が返ったら検索結果からもその人を除く
- 検索結果のキャッシュは、検索語（前後の空白を除いたもの）ごとに分ける。小文字にはそろえない（JS の小文字化と PostgreSQL の `ILIKE` が同じ結果になる保証が無いので、大小だけ違う語は別に持つ。損は 1 回余分に読むだけ）

## 3. API

`GET /api/users?q=<語>&cursor=&limit=`

| 応答 | 場面 |
| --- | --- |
| 200 UserCard の一覧（id の降順） | 成功。該当なしは `items` が空 |
| 422 `VALIDATION_ERROR` | `q` が無い、空、空白だけ、51 文字以上、使えない文字を含む。field は `q` |
| 400 `BAD_REQUEST` | `cursor` が UUID でない、`limit` が 1〜50 の範囲外、`q` などの書き方（`%` の後ろ）が壊れている |
| 401 `UNAUTHENTICATED` | 未ログイン |

`q` が無いときも 400 でなく 422 にする（空のときと同じ扱いにそろえる）。`cursor` は前の応答の `nextCursor`（返した最後の人の `id`）をそのまま送る。

422 の文言は次のとおり。

| 場面 | 文言 |
| --- | --- |
| 無い・空・空白だけ | 検索する語を入力してください |
| 51 文字以上 | 50 文字以内で入力してください |
| NUL と、対になっていないサロゲートを含む | 使えない文字が含まれています |

検証の順序は次のとおり（投稿・コメント本文の規則と同じ）。

1. 受け取ったままの値に使えない文字があれば誤りにする
2. `TextRules.stripBlank` で前後の空白を取り除く。全角空白と U+00A0（改行しない空白）も空白として扱い、画面の `trim()` が除く文字にそろえる（投稿の本文と同じ。[api-conventions.md](../api-conventions.md)）。`trim()` は NUL も消してしまうので使わない
3. 空なら誤りにする
4. 長さがコードポイントで 50 を超えれば誤りにする。絵文字などは 1 文字と数える

使うのは、前後の空白を除いた後の値。検索語は利用者が自由に打つ文字なので、ログには書かない（要求ログの `url.query` では値を `***` に置き換える。[logging-design.md](../logging-design.md) の 5 章）。

## 4. 処理の流れ

1. `q` を検証し（3 章）、`\`、`%`、`_` の順にエスケープして、前後に `%` を付けたパターンを作る。`\` を先に置き換えるのは、先に `%` や `_` を `\%`・`\_` にすると、そのとき足した `\` まで次の置き換えで二重になるため
2. `username ILIKE パターン ESCAPE '\' OR display_name ILIKE パターン ESCAPE '\'` で `users` を引き、id の降順に `limit + 1` 件。2 つの条件を 1 つの `WHERE` に OR で書き、結合しないので、両方に一致しても 1 行。`cursor` があれば `AND u.id < cursor` を足す
3. 各行に `isFollowing` を付ける。行ごとに `EXISTS`（自分がその人をフォローしているか）で求める
4. `limit + 1` 件目があれば、`limit` 件に切って `nextCursor` に最後の人の `id` を入れる

読む列は表示に要るものだけ（`email` と `password_hash` は読まない）。値はすべて `#{}` で渡す。

索引は付けない。数百人の規模なら全件走査で十分（[database-design.md](../database-design.md) の 4 章）。

## 5. データ

`users`、`follows`（`isFollowing`）。

## 6. テストの期待一覧

### 正常系

- ユーザー名の一部で探すと、その人が返る
- 表示名の一部で探すと、その人が返る
- `ALI` で `alice` が返る（大文字小文字を区別しない）
- 自分も結果に出る
- フォローしている人の `isFollowing` が true

### 入力の境界

- `q` が無い、空、空白だけは 422
- 1 文字は通る。50 文字は通る、51 文字は 422
- 前後の空白は取り除かれる（` ali ` で `alice` が返る）。全角空白だけ、U+00A0 だけは空白として 422
- 絵文字 50 個は通り、51 個は 422（コードポイントで数える）
- `cursor` が UUID でない、`limit` が 0 や 51 は 400
- `%` を含む語で全員が返らない。`_` を含む語で任意の 1 文字に一致しない（エスケープされている）
- `\` を含む語（末尾が `\` の語も）で 500 にならず、`\` を文字として探す
- NUL 文字や、対になっていないサロゲートを含む `q` は 422（文言は「使えない文字が含まれています」）

### 権限

- 未ログインは 401

### 異常系

- 画面: 読み込みに失敗したら「再試行」が出る

### 重複と一意性

- ユーザー名と表示名の両方に一致しても、その人は 1 回だけ返る

### 並び順とページング

- id の降順。21 人なら `items` が 20 で `nextCursor` が 20 件目の id。`cursor` で続きが重複なく返る
- 続きの目印（`nextCursor`）の人が、続きを読む前に退会しても、続きは欠けも重複も無く返る（残りの 1 人だけ）

### 画面

- 入力が止まって 400 ミリ秒後に検索され、URL に `?q=` が付く。リロードしても同じ結果
- Enter を押すとすぐ検索される
- 入力を空にすると初期状態に戻り、URL から `q` が消える
- 51 文字以上は文言が出て検索されない
- 入力中に「戻る」を押しても 1 文字ずつ戻らず、検索の前の画面に戻る
- 古い検索の応答が後から返っても、新しい結果を上書きしない
- 自分のカードにフォローボタンが出ない
- 該当なしの文言が出る
- 入力してすぐ Enter を押しても、あとからタイマーがもう一度検索したり URL を書き換えたりしない。変換を確定する Enter の直後も、確定した語で 1 回だけ検索する
- 日本語の変換中は検索せず、確定してから検索する
- 検索画面にいるまま「検索」のリンクを押す、「戻る」「進む」を押すと、欄と表示が URL に従う。待っていたタイマーが古い語で URL を書き戻さない
- 入力中の末尾の空白（「ali 」）が、URL の書き換えで欄から消えない
- URL を手で書いた `q` で開く。51 文字以上は誤りの文言が出て、API を呼ばない。空白だけは初期状態。絵文字 50 個は検索される（絵文字 1 個を 1 文字と数える）。NUL を含むときは API の 422 の文言が欄の下に出て、「再試行」は出ない
- 検索語が変わったら、前の結果はすぐ消えて読み込み中の印が出る
- 結果でフォローすると、ほかの一覧やプロフィールの同じ人も変わる。プロフィールでフォローすると、検索結果のボタンも変わる
- 見出し「検索」がある。欄に `aria-label` がある

## 7. 手動確認の手順

1. 検索欄に他人のユーザー名の一部を入れて少し待つ → 自動で結果に出る。URL に `?q=` が付く。Enter を押すとすぐ出る
2. 表示名の一部（日本語）で検索 → 出る
3. 結果のフォローボタンでフォロー → ボタンが変わる。その人のプロフィールを開くと「フォロー中」で、戻ると検索結果のボタンも「フォロー中」のまま
4. 「戻る」→ 検索の前の画面に戻る（1 文字ずつ戻らない）
5. 51 文字を入れる → 「50 文字以内で入力してください」が出て、URL に `q` が付く。リロードしても同じ誤りが出る
6. 検索画面で、下部タブ（PC は左ナビ）の「検索」を押す → 欄が空になり「ユーザー名か表示名で探せます」に戻る
7. `/search?q=a%00b` を開く → 欄の下に「使えない文字が含まれています」が出て、「再試行」は出ない
8. `%`・`_` で検索 → 全員は出ない（名前にその文字を含む人だけ）
9. 360px 幅で、欄と結果のカードが横にはみ出さない。自分のカードにはフォローボタンが出ない。PC 幅では見出し「検索」が見え、スマホ幅では上部バーの「検索」だけが見える
10. `docker compose stop backend` で backend を止めてから検索 → 「再試行」が出る（確かめたら `docker compose start backend`）

日本語の変換（IME）は自動の確認用ブラウザでは起こせないので、`SearchBox.test.tsx` の変換のテストで代える。
