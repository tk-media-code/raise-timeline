# ユーザー検索

- 日付: 2026-10-06
- 要件: [requirements.md](../requirements.md) の 3.8
- 設計: [api-conventions.md](../api-conventions.md)、[database-design.md](../database-design.md) の 4〜5 章
- Issue: 実装の順序の 8「ユーザー検索を作る」

## 1. 概要

ユーザー名と表示名の部分一致でユーザーを探す。大文字小文字を区別しない。結果からプロフィールへ移り、その場でフォローできる。

## 2. 画面 `/search`

| 要素 | 内容 |
| --- | --- |
| 検索欄 | 上部。Enter か検索ボタンで検索。URL の `?q=` に反映する。開いたときに `q` があればそれで検索する |
| 結果 | ユーザーカードの無限スクロール。自分も出るが、自分にはフォローボタンが出ない |
| 初期状態 | 「ユーザー名か表示名で探せます」 |
| 該当なし | 「該当するユーザーがいません」 |
| 誤り | 空や空白だけでは検索しない。51 文字以上は「50 文字以内で入力してください」 |

- ブラウザの「戻る」で前の検索語と結果に戻れる（URL に持たせるため）

## 3. API

`GET /api/users?q=<語>&cursor=&limit=`

| 応答 | 場面 |
| --- | --- |
| 200 UserCard の一覧（id の降順） | 成功。該当なしは `items` が空 |
| 422 `VALIDATION_ERROR` | `q` が無い、空白だけ、51 文字以上 |

`q` は前後の空白を取り除いてから使う。

## 4. 処理の流れ

1. `q` を検証し、`%` と `_` と `\` をエスケープする
2. `username ILIKE '%q%' OR display_name ILIKE '%q%'` で `users` を引き、id の降順に `limit + 1` 件
3. 各行に `isFollowing` を付ける

索引は付けない。数百人の規模なら全件走査で十分（[database-design.md](../database-design.md) の 4 章）。

## 5. データ

`users`、`follows`（`isFollowing`）。

## 6. テストの期待一覧

### 正常系

- ユーザー名の一部で探すと、その人が返る
- 表示名の一部で探すと、その人が返る
- `ALI` で `alice` が返る（大文字小文字を区別しない）
- 自分も結果に出る
- フォローしている人の `isFollowing` が true

### 入力の境界

- `q` が無い、空、空白だけは 422
- 1 文字は通る。50 文字は通る、51 文字は 422
- 前後の空白は取り除かれる（` ali ` で `alice` が返る）
- `%` を含む語で全員が返らない。`_` を含む語で任意の 1 文字に一致しない（エスケープされている）

### 権限

- 未ログインは 401

### 異常系

- 画面: 読み込みに失敗したら「再試行」が出る

### 重複と一意性

- ユーザー名と表示名の両方に一致しても、その人は 1 回だけ返る

### 並び順とページング

- id の降順。21 人なら `items` が 20 で `nextCursor` が 20 件目の id。`cursor` で続きが重複なく返る

### 画面

- Enter で検索され、URL に `?q=` が付く。リロードしても同じ結果
- 自分のカードにフォローボタンが出ない
- 該当なしの文言が出る

## 7. 手動確認の手順

1. 検索欄に他人のユーザー名の一部を入れて Enter → 結果に出る。URL に `?q=` が付く
2. 表示名の一部で検索 → 出る
3. 結果のフォローボタンでフォロー → ボタンが変わる
4. 「戻る」→ 前の検索に戻る
