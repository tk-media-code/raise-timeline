# タイムライン

- 日付: 2026-10-06
- 要件: [requirements.md](../requirements.md) の 3.4
- 設計: [api-conventions.md](../api-conventions.md) の 2 章（カーソル）、[database-design.md](../database-design.md) の 5 章
- Issue: 実装の順序の 3「投稿とタイムラインを作る」（すべて）、9「フォローを作る」（フォロー中）

## 1. 概要

ホームに投稿を新しい順に並べる。「フォロー中」は自分とフォローしている人の投稿、「すべて」は全員の投稿。20 件ずつの無限スクロール。

## 2. 画面 `/`

| 要素 | 内容 |
| --- | --- |
| 投稿フォーム | 上部。[post.md](post.md) |
| タブ | 「フォロー中」「すべて」。URL の `?tab=following` / `?tab=all` に反映する。省くとフォロー中 |
| 一覧 | 投稿カードの無限スクロール。末尾が見えたら次の 20 件を読む |
| 空の状態 | フォロー中: 「まだ投稿がありません。「すべて」から気になる人をフォローしてみましょう」。すべて: 「まだ投稿がありません」 |
| 終端 | 「これ以上ありません」 |
| 失敗 | 「読み込みに失敗しました」と「再試行」 |

- タブを切り替えると URL が変わり、リロードしてもタブが保たれる
- 投稿すると、表示中のタブの先頭に新しい投稿が出る
- タブごとに TanStack Query のキー（`['timeline', 'following']` / `['timeline', 'all']`）を分け、切り替えで読み直さない
- Issue 3〜8 のあいだは「すべて」のタブ 1 つだけで、既定も「すべて」。URL の `tab` はまだ読まない（`/?tab=following` と打っても「すべて」が出る）。「フォロー中」と `tab` の扱いは Issue 9 で足す（[requirements.md](../requirements.md) の「Issue ごとの仮の振る舞い」）。1 つしかないタブを URL に反映しても読み手が居ないため、読む側と一緒に Issue 9 で入れる
- タブの並びの名前は「タイムラインの種類」、一覧の名前は「タイムライン」（読み上げ用）
- 一覧の投稿カードは相対時刻で、押すと投稿詳細（`/posts/:id`）へ移る。投稿の操作は [post.md](post.md)
- 一覧の取得は、失敗したらすぐ「読み込みに失敗しました」と「再試行」を出す。TanStack Query の既定の自動再試行（3 回まで間を置く）と、前面に戻るたびの取り直しは止めている（`queryClient` の既定は `retry: false`、`refetchOnWindowFocus: false`）。自動で再試行すると失敗の表示が遅れ、前面に戻るたびに取り直すと、無限スクロールで読み込んだ全ページを取り直してしまうため

## 3. API

| API | 入力 | 応答 |
| --- | --- | --- |
| `GET /api/timeline/following` | cursor, limit | 200 Post の一覧。自分とフォロー相手の投稿 |
| `GET /api/timeline/all` | cursor, limit | 200 Post の一覧。全員の投稿 |

どちらも id の降順。`limit` は 1〜50、省くと 20。

## 4. 処理の流れ

1. 投稿者を結合した本体の SQL で `limit + 1` 件を取る（[database-design.md](../database-design.md) の 5 章）
2. 投稿 id の集合に対して、画像・いいね数・コメント数・自分がいいね済みかを、それぞれ 1 本の問い合わせでまとめて取る（投稿ごとに取りに行かない。1 ページあたり 5 本で固定）。Issue 3〜6 では `likeCount` を 0、`likedByMe` を false、Issue 3〜7 では `commentCount` を 0 で返す
3. 画像のキーを URL に変換する
4. 余分な 1 件があれば `nextCursor` に `limit` 件目の id を入れる

### 画面のキャッシュの書き換え

投稿・編集・削除が成功したら、一覧（TanStack Query のキー `['timeline', 'all']`）と投稿詳細（`['post', id]`）のキャッシュを直接書き換える。`invalidateQueries` で取り直すと、無限スクロールで読み込んだ全ページを順に取り直してしまう（遅く、スクロール位置の先も入れ替わる）ため。投稿は「すべて」の 1 ページ目の先頭に足す（まだ読み込んでいなければ何もしない。開いたときに最新が取れる）。編集は一覧の全ページと詳細の同じ投稿を置き換える。削除は一覧から除き、詳細のキャッシュを捨てる。

書き換えと読み込みが重なるときの扱いは次のとおり。

- **次のページを読み込み中のとき**: 書き換える前に、その読み込みを取り消す。無限読み込みは取得を始めた時点のキャッシュを土台にページを足すので、取り消さないと、届いたページで書き換えが上書きされる（削除した投稿が戻る、編集が元に戻る、新しい投稿が消える）。取り消した続きは、一覧の末尾が見えていれば読み直される
- **最初の読み込みの途中のとき（まだデータが無い。投稿と編集だけ）**: 書き換える前には取り消さない。取り消すだけだと待機中に戻って誰も取り直さず、一覧が読み込み中のまま止まる。書き換える先も無い。代わりに、成功のあとで、その読み込みを取り消してすぐ今の状態から取り直す。届くページは変更の前の状態なので、そのままだと「投稿しました」と出るのに新しい投稿が見えないため。削除は対象にしない。削除するにはカードが表示されている必要があり、その一覧は読み込み済みのため
- 編集・削除が 404（もう無い）で終わったときは、その投稿を一覧と詳細のキャッシュから除き、一覧は取り直しも出す

## 5. データ

`posts`、`follows`（フォロー中）、`post_images`、`likes`、`comments`。

## 6. テストの期待一覧

### 正常系

- 「すべて」に全員の投稿が新しい順に返る
- 「フォロー中」に自分の投稿とフォロー相手の投稿だけが返る。フォローしていない人の投稿は返らない
- 誰もフォローしていなければ「フォロー中」は自分の投稿だけ
- 各投稿に `likeCount`、`commentCount`、`likedByMe` が正しく付く
- 画面: 投稿すると表示中のタブの先頭に出る

### 入力の境界

- 投稿が 0 件なら `items` が空で `nextCursor` が null
- 20 件ちょうどなら `nextCursor` が null
- 21 件あれば `items` が 20 件で `nextCursor` が 20 件目の id
- `limit=50` は通る、`limit=51` と `limit=0` は 400
- `cursor` が UUID でなければ 400

### 権限

- 未ログインは 401

### 異常系

- 画面: 読み込みに失敗したら「再試行」が出て、押すと読み直す。自動では再試行しない
- 画面: 次のページを読み込んでいる最中に削除・編集・投稿が成功しても、届いたページで書き換えが上書きされない（削除した投稿が戻らない、編集が元に戻らない、新しい投稿が消えない）
- 画面: 最初の読み込みの最中に投稿が成功しても、新しい投稿が先頭に出る。一覧が読み込み中のまま止まらない

### 重複と一意性

- 2 ページにまたがって同じ投稿が出ない
- 1 ページ目を読んだあとに新しい投稿が増えても、2 ページ目にずれや重複が出ない（カーソルは id なので影響しない）
- 続きの目印（`cursor`）にした投稿が削除されていても、それより古い投稿が欠けも重複も無く返る

### 並び順とページング

- `items` が id の降順
- `cursor` を付けると、返る投稿はすべて `cursor` より古い（id が小さい）
- 「フォロー中」でも並びと `nextCursor` は同じ規則

### 画面

- タブを切り替えると URL の `tab` が変わる。リロードでタブが保たれる
- 末尾が見えると次が読まれ、読み込み中の表示が出る。最後は「これ以上ありません」
- フォロー中が空のとき、案内の文言が出る

## 7. 手動確認の手順

1. 25 件以上投稿し、ホームで下までスクロール → 20 件のあとに続きが読まれ、最後に「これ以上ありません」
2. 「すべて」に切り替え → URL に `?tab=all`。リロードしても「すべて」のまま
3. 別のユーザーで投稿 → 「すべて」には出るが、フォローしていなければ「フォロー中」には出ない
4. フォローする → 「フォロー中」に出る
