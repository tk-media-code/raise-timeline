# 登録・ログイン・ログアウト・退会

- 日付: 2026-10-06
- 要件: [requirements.md](../requirements.md) の 3.1
- 設計: [auth-design.md](../auth-design.md)、[error-handling-design.md](../error-handling-design.md)
- Issue: 実装の順序の 2「認証の基盤を作る」。退会は 6「退会を作る」

## 1. 概要

利用者がアカウントを作り、ログインし、ログアウトし、必要なら退会する。ログインの持続はアクセストークンとリフレッシュトークンで行う。退会は Issue 6 で作った。
この Issue は認証の基盤でもあり、`users` と `refresh_tokens` のテーブル、Spring Security のエラー応答と利用者 id のログ（[logging-design.md](../logging-design.md) の 13 章）、
Vite の proxy、フロントの API クライアント・認証状態・共通レイアウトも一緒に作る。

## 2. 画面

### 登録 `/register`

| 項目 | 入力 | 検証（画面とサーバーで同じ） | 誤りの文言 |
| --- | --- | --- | --- |
| ユーザー名 | テキスト | 3〜20 文字。英数字と `_` だけ | 3〜20 文字の英数字と _ で入力してください |
| 表示名 | テキスト | 1〜50 文字（空白だけは不可） | 1〜50 文字で入力してください |
| メールアドレス | email | メールアドレスの形式。254 文字以内 | メールアドレスの形式で入力してください |
| パスワード | password | 8〜72 文字。空白を含まない半角の英数字と記号 | 8〜72 文字の半角英数字と記号で入力してください |

- ボタン「登録する」。送信中は無効
- リンク「ログインはこちら」→ `/login`
- 成功したらログイン済みとして `/` へ移る
- 409 は該当する項目の下に「このユーザー名は使われています」「このメールアドレスは登録済みです」
- 表示名の前後の空白は取り除いてから検証し、保存する

### ログイン `/login`

| 項目 | 入力 |
| --- | --- |
| メールアドレス | email |
| パスワード | password |

- ボタン「ログイン」。送信中は無効
- リンク「アカウントを作る」→ `/register`
- 失敗はフォーム上部に「メールアドレスまたはパスワードが違います」。どちらが違うかは言わない
- 成功したら `?next=` があればそこへ、無ければ `/` へ
- ログイン済みで開いたら `/` へ移す

### ログアウト

左ナビ（PC）または上部バーのメニュー（スマホ）の「ログアウト」→ 確認ダイアログ → `POST /api/auth/logout` → 状態を捨てて `/login` へ。

### 退会（プロフィール編集画面の末尾）

| 要素 | 内容 |
| --- | --- |
| 節の見出し | 「退会」 |
| 説明 | 「退会すると、投稿・コメント・いいね・フォロー・画像がすべて消え、元に戻せません。」 |
| ボタン | 「退会する」（危険な操作の見た目） |
| ダイアログ | 見出し「本当に退会しますか？」、同じ説明、パスワードの入力欄（ラベル「パスワード」、`autocomplete="current-password"`）、ボタン「取り消し」（既定のフォーカス）と「退会する」。送信中でなければ Esc と「取り消し」で閉じる。背景の押下では閉じない（確認や入力のダイアログ（`ConfirmDialog`、投稿の作成・編集）と同じ。画像ビューアだけは背景で閉じる）。送信中は両方のボタンを無効にし、Esc でも閉じない |
| 誤り | 空は「入力してください」、違えば「パスワードが違います」を入力欄の下に出し、ダイアログは閉じない。入力は残す。429 は「しばらく待ってから再試行してください」を、500 や通信の失敗は失敗の文言（500 は requestId 付き）を、ダイアログの上部に出す。401 `UNAUTHENTICATED`（更新も失敗）は何も出さない |
| 成功 | `DELETE /api/users/me` → 状態（アクセストークン、利用者、TanStack Query のキャッシュ）を捨て、他のタブへ知らせ、通知「退会しました」、`/login` へ（`next` は付けない） |

- 他人が端末を触っただけでは退会できないよう、パスワードの再入力を求める
- 退会したあとは、同じユーザー名とメールアドレスで再び登録できる
- 退会が済んだら、ログアウトと同じく他のタブへ知らせる。他のタブが、退会した人の画面のまま残らないようにするため。受け取ったタブは取り直しの更新が 401 になり、ログイン画面へ移る
- エラーの出し分けは、誤りを見せる場所で決める。パスワードが原因のもの（401 `INVALID_PASSWORD`、422 の `password`）は入力欄の下。入力欄に結べないもの（429、500、通信の失敗）はダイアログの上部。401 `UNAUTHENTICATED` は、画面が未ログインにしてログイン画面へ移るので何も出さない。429 は nginx が返す HTML で Problem Details ではなく、既定の文言は「通信に失敗しました」になってしまうため、ステータスで文言を決める
- ブラウザがダイアログを強制的に閉じることがある（Esc の連打、Android の戻る操作）。これは止められず、止めようとすると `<dialog>` だけが閉じて親の状態が開いたまま残り、開き直せなくなる。そのときは親の状態も閉じ、送信中の要求は続ける。成功すれば通知と状態の破棄はそのまま行われ、失敗すれば誤りを見せる欄が無いので、同じ文言を通知（toast）で出す
- 背景の押下で閉じないのは、確認や入力のダイアログ（`ConfirmDialog`、投稿の作成・編集）の実際の動きと同じにするため（画像ビューアだけは背景で閉じる）。設計の段階では「背景でも閉じる」と考えていたが、確認や入力のダイアログは背景では閉じないので、そろえた。`ModalDialog` は、これらのダイアログが使う部品の名前

## 3. API

### `POST /api/auth/register`

```json
{ "username": "alice", "displayName": "アリス", "email": "alice@example.com", "password": "correct-horse-1" }
```

| 応答 | 場面 |
| --- | --- |
| 201 `{ "accessToken": "...", "user": Me }`（email を含む。[api-conventions.md](../api-conventions.md) の 3 章）＋ `Set-Cookie: refresh_token=...` | 成功 |
| 409 `USERNAME_TAKEN` / `EMAIL_TAKEN` | 重複。`errors` に項目 |
| 422 `VALIDATION_ERROR` | 検証の失敗 |

### `POST /api/auth/login`

```json
{ "email": "alice@example.com", "password": "correct-horse-1" }
```

| 応答 | 場面 |
| --- | --- |
| 200 `{ "accessToken": "...", "user": Me }` ＋ Cookie | 成功 |
| 401 `INVALID_CREDENTIALS` | メールアドレスが無い、またはパスワードが違う |
| 422 | 項目が空 |

### `POST /api/auth/refresh`

入力は Cookie だけ。

| 応答 | 場面 |
| --- | --- |
| 200 `{ "accessToken": "...", "user": Me }` ＋ 新しい Cookie | 有効なリフレッシュトークン |
| 401 `INVALID_REFRESH_TOKEN`（Cookie は消さない） | 無い、期限切れ、ログアウト済み、使用済み |

### `POST /api/auth/logout`

入力は Cookie だけ。常に 204 で、Cookie を消す。該当する `refresh_tokens` の行を消す。

### `DELETE /api/users/me`

```json
{ "password": "correct-horse-1" }
```

| 応答 | 場面 |
| --- | --- |
| 204 ＋ Cookie を消す | 成功。利用者と、その投稿・画像・いいね・コメント・フォロー関係・リフレッシュトークンを消し、S3 の画像をコミット後に消す |
| 401 `INVALID_PASSWORD` | パスワードが違う。何も消えない |
| 422 | パスワードが空 |
| 401 `UNAUTHENTICATED` | 未ログイン。または、アクセストークンの有効な間に本人の行がもう無い（2 つのタブでほぼ同時に退会した、後のほう） |

### `GET /api/health`

ログ基盤の Issue（実装の順序 1）で `GET /` から `/api/health` へ移す。この Issue では変えない（[logging-design.md](../logging-design.md) の 13 章）。

## 4. 処理の流れ

[auth-design.md](../auth-design.md) の 3 章。

退会は次の順で行う。

1. 利用者の行を引き、無ければ 401 `UNAUTHENTICATED`（照合の前。認証を通ったあとに退会された場合で、「本人の行がもう無ければ 401」というほかの API の決まりにそろえる）
2. パスワードを照合する（BCrypt。トランザクションの外で先に行い、違えば 401 `INVALID_PASSWORD`）
3. トランザクションを始め、`SELECT id FROM users WHERE id = #{me} FOR UPDATE` で利用者の行を押さえる。同じ人の進行中の投稿やアイコンの更新を待ち、新しい挿入を止めるため（押さえないと、キーを集めた後に入った画像が S3 に残る）。行が無ければ（照合の間に、別のタブの退会が済んだ）401 `UNAUTHENTICATED`
4. 消す S3 のキー（`post_images` を `posts.user_id` でたどった投稿画像と、`users.avatar_key`）を集める
5. `users` の行を消す。外部キーの `ON DELETE CASCADE` で、投稿・画像の行・いいね・コメント・フォロー関係・リフレッシュトークンが消える
6. コミットしたあとに、出来事 `user.withdrew` を INFO で残し（利用者 id は MDC にある。[logging-design.md](../logging-design.md) の 3 章）、集めたキーを S3 からまとめて消す。失敗は `image.delete_failed`（WARN。消せなかったキーを載せる）で、応答は 204
7. Cookie を消して 204 を返す

パスワードが違うときは出来事を残さない（`auth.login.failed` のような出来事は作らない）。

退会と同時に走った同じ人の投稿などが利用者への外部キー違反になったときは、401 `UNAUTHENTICATED` に変換する（[error-handling-design.md](../error-handling-design.md)）。

退会と、同じ人のトークンの更新が同時に走ると、まれに DB のデッドロックで片方が 500 になる。更新はトークンの行を消してから `users` に依存する行を入れ、退会は `users` の行を押さえてからトークンの行を消すので、ロックの順が逆になるため。PostgreSQL が片方を取り消すのでデータは壊れず、利用者はやり直せば済むので、受け入れる。順を揃えるために退会の `FOR UPDATE` をやめると、進行中の投稿を待てず、S3 に画像が残る。

退会と同時のログインは、照合（BCrypt）の間に本人が退会してコミットすると、トークンの挿入が `refresh_tokens_user_id_fkey` の外部キー違反になる。これは 500 にせず、メールアドレスが無い場合と同じく `auth.login.failed` を INFO で残して 401 `INVALID_CREDENTIALS` にする（ほかの制約の違反は変換せず 500）。

退会のあとも、残っているアクセストークンは最長 1 時間は署名が有効なので、認証のたびに利用者の存在を確かめて 401 にする（[auth-design.md](../auth-design.md) の 6 章）。

## 5. データ

`V1__users.sql` で `users` と `refresh_tokens` を作る（[database-design.md](../database-design.md)）。退会の連鎖削除のため、後の Issue で作る `likes` と `comments` には `user_id` の索引を付ける。

## 6. テストの期待一覧

### 正常系

- 正しい入力で登録すると 201。応答に `accessToken` と `user`（`isMe` が true、`email` を含む）が入り、`refresh_token` の Cookie が付く
- 登録したメールアドレスとパスワードでログインすると 200
- ログインで返った Cookie で更新を呼ぶと 200。新しい `accessToken` と新しい Cookie が返る
- 更新のあと、古いリフレッシュトークンで更新を呼ぶと 401（使い捨て）
- ログアウトのあと更新を呼ぶと 401
- `accessToken` を付けて `GET /api/users/me` を呼ぶと 200
- 応答の `user` にパスワードのハッシュが含まれない。DB のハッシュは `$2` で始まる（BCrypt）

### 入力の境界

- ユーザー名: 2 文字は 422、3 文字は通る、20 文字は通る、21 文字は 422。ハイフンや日本語を含むと 422
- 表示名: 空白だけは 422、1 文字は通る、50 文字は通る、51 文字は 422。絵文字 1 つは 1 文字と数える
- メールアドレス: `@` が無いと 422。255 文字は 422
- パスワード: 7 文字は 422、8 文字は通る、72 文字は通る、73 文字は 422。全角文字を含むと 422
- ログインで項目が空だと 422
- 表示名に NUL 文字を含むと 422（ユーザー名・メールアドレス・パスワードも同じ。共通の検証）

### 権限

- トークン無しで `GET /api/users/me` は 401 `UNAUTHENTICATED`
- 期限切れのトークンは 401
- 署名が違うトークンは 401
- 他人のプロフィール（`GET /api/users/{username}`）と各一覧の応答に `email` が含まれない
- 画面: 未ログインで `/` を開くと `/login?next=/` へ移り、ログイン後に `/` へ戻る
- 画面: ログイン済みで `/login` を開くと `/` へ移る
- 署名の方式を `none` にしたトークン（署名なし）は 401
- 画面: 戻り先に `//evil.example`、`/\evil.example`、`https://evil.example`、タブを混ぜた `/%09/evil.example` を渡してログインすると、外へは移らず `/` へ移る

### 異常系

- DB に届かないとき、ログインは 500 で、本文に原因が無い
- 画面: API が 401 `UNAUTHENTICATED` を返したら、更新を 1 回だけ呼び、成功なら元の要求をやり直す。更新も 401 なら `/login` へ移る。ログイン失敗の 401 `INVALID_CREDENTIALS` では更新を呼ばない
- 画面: 同時に複数の要求が 401 になっても、更新は 1 回しか呼ばれない
- 画面: 起動時の更新と API クライアントの更新が同じ 1 本にまとめられる（StrictMode で effect が 2 回走っても更新は 1 回）
- 更新が 401 を返しても Cookie は消えない
- 更新を同時に 2 本送ると、片方だけが 200 で、もう片方は 401（引くと消すが 1 文で行われている）
- 画面: ログアウトすると TanStack Query のキャッシュが空になる。続けて別の人がログインしても、前の人のデータが出ない
- 画面: API クライアントは、本文が JSON でない応答（nginx の HTML の 413・429）と通信の失敗を、`code` が null の `ApiError` にする。例外で画面が止まらない
- 画面: 500 の通知に requestId が全桁出る（[logging-design.md](../logging-design.md) の 6 章）
- 画面: 部品が描画中に例外を投げると、ErrorBoundary の「問題が起きました。再読み込みしてください」の画面が出る
- 画面: 存在しない URL で「ページが見つかりません」の画面とホームへのリンクが出る

### 重複と一意性

- 同じユーザー名で 2 回登録すると 409 `USERNAME_TAKEN`。`errors` に `username`。`Alice` と `alice` も重複
- 同じメールアドレスで 2 回登録すると 409 `EMAIL_TAKEN`。大文字小文字が違っても重複
- 同時に同じユーザー名で登録しても 1 人だけ作られ、もう一方は 409

### 並び順とページング

この機能には無い。

### その他

- ログイン失敗の文言は、存在しないメールアドレスでも、パスワード違いでも同じ
- パスワードとトークンは、DEBUG を含むどのログの行にも含まれない。メールアドレスは INFO 以上の行に含まれない（DEBUG の行に出るローカルの SQL の引数は見ない。[logging-design.md](../logging-design.md) の 5 章）
- ログイン失敗の応答時間が、メールアドレスの有無で変わらない（ダミーの照合をしている）
- 登録、ログインの成功と失敗、更新の失敗、ログアウトが、出来事 `auth.register` `auth.login.succeeded` `auth.login.failed` `auth.refresh.failed` `auth.logout` として残る。成功の行には利用者 id が付き、失敗の行にはメールアドレスの有無を示す値が無い（[logging-design.md](../logging-design.md) の 3 章）

### 退会

- 正しいパスワードで退会すると 204。`users` にその行が無く、Cookie が消える
- 退会すると、その人の投稿・画像の行・いいね・コメント・フォロー関係（両方向）・リフレッシュトークンが消える（Mapper。いいね・コメント・フォローは Issue 7〜9 で確かめる）
- S3 の代役の `deleteAll` に、その人の投稿画像とアイコンのキーがすべて渡る
- 退会したあと、同じユーザー名とメールアドレスで再び登録できる
- 他の利用者の投稿・いいね・コメント・フォロー関係は残る。自分の投稿に他人が付けたいいね・コメントは消える
- パスワードが空なら 422。違えば 401 `INVALID_PASSWORD` で、何も消えない
- 未ログインは 401
- 退会のあと、古いアクセストークンで `GET /api/users/me` を呼ぶと 401 `UNAUTHENTICATED`。同じユーザー名で再登録した後も、古いトークン（別の id）は 401 のまま
- S3 の削除が失敗しても 204 で、WARN の出来事 `image.delete_failed` に消せなかったキーが載る
- 退会が出来事 `user.withdrew` として利用者 id 付きで残る
- 照合の前に本人の行が無ければ 401 `UNAUTHENTICATED` で、照合しない。押さえる時点で行が無ければ（同時に退会した後のほう）401 で、何も消さず S3 も触らない
- 照合はトランザクションの外で行う。パスワードが違えば行を押さえず、何も消さず、S3 も触らない
- 画面: ダイアログの文言が表のとおり。パスワード違いで入力欄の下に文言が出てダイアログは閉じない。成功で通知が出て `/login` へ移る
- 画面: 429 と 500 はダイアログの上部に文言が出る。401 `UNAUTHENTICATED` は何も出さない
- 画面: 送信中でなければ Esc と「取り消し」で閉じ、背景の押下では閉じない。送信中は両方のボタンが押せず、Esc でも閉じない
- 画面: 送信中にブラウザに閉じられても親が閉じ、要求は続く。成功すれば通知と状態の破棄が行われ、失敗すれば通知で伝える。閉じたあとにもう一度「退会する」で開き直せる

## 7. 手動確認の手順

1. `docker compose up -d --build` で起動し、`http://localhost:5173/register` で登録する → `/` に移る
2. リロードしても ログイン状態が続く（起動時の更新が通る）
3. ログアウト → `/login` に移り、アドレスバーに `/` を入力して開くと `/login?next=%2F` に戻される
4. ログイン → `/` に戻る
5. ブラウザの開発者ツールで、Cookie に `refresh_token`（HttpOnly）があり、localStorage に何も無いことを見る
6. 同じユーザー名で再登録すると、項目の下に重複の文言が出る
7. `http://localhost:8080/api/health` が 200 を返す
8. 2 つのタブで同時にリロードしても、どちらもログイン済みのまま（Web Locks で更新が順に並ぶ）
9. ブラウザを閉じて開き直し、タブが復元されてもログイン済みのまま
10. プロフィール編集の末尾の「退会する」→ 違うパスワード → 文言が出てダイアログが残る → 正しいパスワード → 「退会しました」と `/login`
11. 退会した人の投稿が他の人のタイムラインから消えている。同じユーザー名で再登録できる
12. 同じブラウザの別のタブで開いていた画面も、退会するとログイン画面に移る
