# いいね

- 日付: 2026-10-06
- 要件: [requirements.md](../requirements.md) の 3.5
- 設計: [api-conventions.md](../api-conventions.md)、[database-design.md](../database-design.md)
- Issue: 実装の順序の 7「いいねを作る」

## 1. 概要

投稿にいいねを付ける・外す。1 人 1 回。自分の投稿にも付けられる。いいねした人の一覧を見られる。

## 2. 画面

### いいねボタン

- ハートと数。付けていれば塗りつぶしの ♥（`text-pink-600`）、いなければ ♡。ボタンの名前は「いいね n 件」のままにして、`aria-pressed` で状態を伝える（[requirements.md](../requirements.md) の 6 章で決めた名前）
- 押した瞬間に見た目と数を変え、裏で API を呼ぶ。失敗したら元に戻して通知する（楽観的更新）
- 一覧のカードでは、ハートと数で 1 つのボタンにする。投稿詳細では、ハート（付け外しのボタン）と数（「いいねした人」へのリンク、名前は「いいねした人を見る（n 件）」）に分ける。どちらも 44px 四方以上にする。プロトタイプでは数のリンクが幅 32px で押しにくかった
- コメント数は Issue 8 まで、押せない表示（`role="img"`）のまま

#### 押したときの画面の動き

- 押すと、キャッシュにある同じ投稿をまとめて書き換える（タイムラインとその人の投稿一覧の全ページ、投稿詳細）。押したカードだけを変えると、画面を移ったときに古い状態が見えるため。投稿の編集と同じやり方
- 連打しても要求は 1 つずつ送り、最後に押した状態に収束させる（`useMutation` の `scope` を投稿ごとに分ける）。送るのは「始まった時点で最後に押した状態」で、保存済みの状態と同じなら送らない
- 途中で失敗したら、「押す直前」ではなく「サーバーに最後に保存できた状態」に戻して通知し、まだ送っていない分は捨てる。「押す直前」に戻すと、連打の途中の失敗で、画面とサーバーの状態が食い違うため
- 失敗の通知は、付けるとき「いいねに失敗しました。もう一度お試しください」、外すとき「いいねの取り消しに失敗しました。もう一度お試しください」。500 で requestId があれば、末尾に「（ID: <requestId>）」を足す。サーバーの文言だけでは、何が失敗したのか分からないため
- 404 は編集・削除と同じ扱いにする。「見つかりません」を通知し、その投稿を一覧から除く。投稿詳細ならホームへ戻す
- その投稿の要求が全部終わったら（成功も失敗も）、その投稿の「いいねした人」のキャッシュを捨てる。次に開いたとき、古い一覧を一瞬見せないため
- ログアウト、ログインの有効期限切れ、別のタブでのログインでは、画面のキャッシュがまとめて捨てられる。そのとき並んでいたいいねの要求も捨てられるので、次に押したときは、その投稿の同期の状態を、表示中の状態から作り直す。捨てられる前から送信中だった要求が後で終わっても、新しい画面のキャッシュは書き換えず、通知も出さない
- 受け入れること: 要求の途中で一覧の読み直しが始まり、その応答が最後の書き直しより後に届くと、古い状態が見えることがある。投稿の編集の応答が、送信中のいいねより古い状態を運ぶことも同じ。どちらも次の読み直しで直る。窓はごく狭く、防ぐには読み込みのたびにいいねの送信中かを照らし合わせる仕組みが要って見合わないため

### いいねした人 `/posts/:id/likes`

- 投稿詳細のいいね数のリンクを押すと移る
- 見出しと、スマホの上部バーの画面名は「いいねした人」
- ユーザーカード（アイコン・表示名・`@ユーザー名`・自己紹介）の無限スクロール。新しい順。押すとプロフィールへ移る。カードの余白を押しても移る（投稿カードの「詳細へ移る」と同じ、マウス向けの近道。リンク・ボタンの上と、文字の選択中は動かない）。Issue 9 のフォローボタンがカードの中に入るので、カード全体は `<a>` にしない
- フォローボタンと `isFollowing` は Issue 9 で足す。それまで `isFollowing` は false
- 0 件なら「まだいいねがありません」
- 投稿が無い（404）か、id が UUID でない（`/posts/abc/likes`。API は 400）ときは、投稿詳細と同じ「見つかりません」の画面にする。URL を打ち間違えた人にとっては、どちらも「無い」ため。ただし、まだ一覧を 1 度も読み込めていないときにこの失敗になった場合だけ。読み込んだ一覧があるときの 404・400（次のページなど）は、一覧を残して「再試行」を出す。それ以外の失敗も「再試行」

## 3. API

| API | 応答 |
| --- | --- |
| `PUT /api/posts/{id}/like` | 204。既に付けていても 204。404 |
| `DELETE /api/posts/{id}/like` | 204。付けていなくても 204。404 |
| `GET /api/posts/{id}/likes` | 200 UserCard の一覧（新しい順）。404 |

## 4. 処理の流れ

- 付ける: `INSERT ... ON CONFLICT DO NOTHING` で行を入れる。既にあれば何もせず 204（一意制約の違反でトランザクションを中断させない）
- 外す: `likes` から行を消す。無くても 204
- 投稿の存在確認: `PUT` は存在を先に確かめず、`INSERT ... ON CONFLICT DO NOTHING` の外部キー違反で投稿の有無を見分ける。`DELETE` は付けていなくても 204 なので、消した行数では投稿の有無が分からない。そのため `DELETE` と一覧は、先に `PostMapper.existsById` で確かめて、無ければ 404 にする（一覧は、投稿が無いのか 0 件なのかを区別する）
- 外部キー違反は制約名で見分ける。`likes_post_id_fkey` は 404 `NOT_FOUND`（付ける直前に投稿が消された）、`likes_user_id_fkey` は 401 `UNAUTHENTICATED`（退会と同時に付けた）。知らない名前は変換せず 500（[error-handling-design.md](../error-handling-design.md)）
- 投稿の `likeCount` と `likedByMe` は、投稿を返すときに `likes` を数える。1 ページの問い合わせは、本体・画像・いいね数・自分のいいねの 4 本で、ページの件数によらない（コメント数は Issue 8 で 5 本目になる）。空のページでは問い合わせない（[timeline.md](timeline.md) の 4 章）
- 一覧: 並びとカーソルは `likes.id`。`nextCursor` には返す最後の行の `likes.id` を入れ、画面はそのまま送り返す。項目は UserCard で、`isFollowing` は Issue 9 まで false 固定にして、SQL に `follows` は出さない（[database-design.md](../database-design.md) の 5 章）。`email` と `password_hash` は読まない
- いいねの出来事のログは足さない。[logging-design.md](../logging-design.md) の 3 章の表に無く、要求ログ（`http.request`）で追えるため

## 5. データ

`V3__likes.sql` で `likes` を作る。一意 `(post_id, user_id)`、索引 `(post_id, id)`。

## 6. テストの期待一覧

### 正常系

- 付けると 204。投稿を取り直すと `likeCount` が 1 増え、`likedByMe` が true
- 外すと 204。`likeCount` が戻り、`likedByMe` が false
- 自分の投稿にも付けられる
- いいねした人の一覧に、付けた人が新しい順に UserCard で返る。`isFollowing` が付く（`isFollowing` は Issue 9 で確かめる。それまでは false）
- タイムラインと投稿詳細の `likeCount`・`likedByMe` が、`likes` を数えた値になる。1 ページの問い合わせは 4 本で、ページの件数によらない
- 投稿を消すと、その投稿のいいねも消える。退会すると、本人のいいねと、本人の投稿へのいいねが消え、他人の投稿の `likeCount` が減る

### 入力の境界

- 一覧が 0 件なら `items` が空で `nextCursor` が null
- 21 人なら `items` が 20 で `nextCursor` が 20 件目の `likes.id`

### 権限

- 未ログインは 401
- 存在しない投稿に付ける・外す・一覧は 404

### 異常系

- 画面: API が失敗したら、ハートと数が元に戻り、通知が出る。付けるときは「いいねに失敗しました。もう一度お試しください」、外すときは「いいねの取り消しに失敗しました。もう一度お試しください」。500 で requestId があれば末尾に「（ID: …）」が付く
- 画面: 連打の途中で失敗したら、「押す直前」ではなく、サーバーに最後に保存できた状態に戻り、まだ送っていない分は送られない
- 画面: 404 なら「見つかりません」が通知され、その投稿が一覧から消える。投稿詳細ならホームへ戻る
- 画面: キャッシュが捨てられたあと（ログアウトなど）は、次に押したときに表示中の状態から同期をやり直す。捨てられる前から送信中だった要求が後で終わっても、新しいキャッシュは書き換わらず、通知も出ない
- 画面: 「いいねした人」で、一覧を 1 度も読み込めないまま 404（投稿が無い）か 400（id が UUID でない）になれば「見つかりません」。読み込んだ一覧があるときの 404・400 は、一覧が残り、「再試行」が出る
- 付ける直前に投稿が消され、外部キー違反（`likes_post_id_fkey`）になったら 404 `NOT_FOUND`。500 にならない（Mapper の代役に外部キー違反を投げさせて確かめる）
- 本人への外部キー違反（`likes_user_id_fkey`。退会と同時に付けた）は 401 `UNAUTHENTICATED`
- Mapper（本物の DB）: 存在しない `post_id` で `likes` に入れると、外部キー違反の制約名が `likes_post_id_fkey` である（代役のテストが打つ名前と、本物の名前が合っていることを確かめる）

### 重複と一意性

- 2 回付けても `likes` は 1 行で、2 回目も 204
- 付けていない投稿を外しても 204
- 同時に 2 回付けても 1 行（`ON CONFLICT DO NOTHING` で 204）

### 並び順とページング

- 一覧は `likes.id` の降順。`nextCursor` は 20 件目の `likes.id` で、`cursor` に付けると続きが重複なく返る

### 画面

- 押した瞬間にハートが塗りつぶされ、数が 1 増える
- 連打しても、要求は 1 つずつ送られ、最後に押した状態に落ち着く。保存済みと同じ状態は送らない
- 一覧のカードではハートと数が 1 つのボタン。投稿詳細ではハートのボタンと、数のリンク（名前は「いいねした人を見る（n 件）」）が別々に押せる
- 数のリンクを押すと一覧へ移る。0 件なら「まだいいねがありません」

## 7. 手動確認の手順

1. タイムラインで投稿にいいねする → 押した瞬間にハートが塗りつぶされ、数が 1 増える。リロードしても保たれる
2. もう一度押す → 外れて、数が戻る
3. 別のユーザーでも同じ投稿にいいねし、投稿詳細の「いいねした人を見る」を押す → 2 人が新しい順に並ぶ。カードを押すとプロフィールへ移る
4. 1 つの投稿のハートを素早く 5 回押す → 最後の状態（付いている）に落ち着き、リロードしても同じ
5. `docker compose stop backend` で backend を止めてから押す → ハートと数が元に戻り、「いいねに失敗しました。もう一度お試しください」が出る（確かめたら `docker compose start backend`）
6. 別のタブで投稿を消してから、元のタブでその投稿にいいねする → 「見つかりません」が出てカードが消える。投稿詳細の画面で同じことをすると、ホームへ戻る
7. いいねの無い投稿の「いいねした人を見る（0 件）」→「まだいいねがありません」。`/posts/<無い id>/likes` →「見つかりません」
8. 360px 幅で、詳細のハートと数のリンクがそれぞれ押せ、横スクロールが出ない。スマホの上部バーの画面名が「いいねした人」
